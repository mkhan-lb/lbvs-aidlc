# AIDLC workflow

Current scope: the engineer-led part of the [Anthropic playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) with committed artifacts, stage gates, requirement-to-check traceability, a bounded review loop, a bug-fix evidence loop, a repository [setup wizard](#repository-setup-with-aidlc-init) and brownfield onboarding, a committed [repository context](#repository-context) (profile, company glossary, playbooks) that stages read before scouting, a pre-PR conventions check, a shipping skill that opens the PR, reused review capability, five plain-Markdown [knowledge stores](#knowledge-stores) and a [platform pointer layer](#platform-and-conventions). No evaluation runner, configuration-regression gate, approval service, delivery execution or maintenance integration is required. Design decisions, project configuration, hosts, MCP servers and the knowledge-store tables are catalogued in [REFERENCE.md](REFERENCE.md).

## The loop

`intent.md` → `spec.md` → `plan.md` → code and ordinary verification → `review.md` / PR findings → fixes and re-review → `/lbvs-aidlc-ship`. Bug fixes add `evidence.md`; proven non-obvious work may add one lesson. Two optional entry helpers come before intent: `/lbvs-aidlc-ticket <KEY>` derives the change and a sourced intent from a Jira or GitHub issue, and `/lbvs-aidlc-spike [change-id]` records a time-boxed investigation in `spike.md` when a question needs depth first. Requirements carry stable IDs from spec to plan to verification ([traceability](#traceability-from-requirement-to-check)).

`/lbvs-aidlc [change-id]` runs this loop. The argument is optional: the orchestrator resolves the change ID itself (see [change IDs](#change-ids-you-do-not-have-to-remember)), states one flow policy for the run, proposes a worktree, reads the project mode, asks the kind of work (**Feature/change**, **Bug fix** → `lbvs-aidlc-fix`, **Spike/investigation** → `lbvs-aidlc-spike`), runs each stage skill in order and stops at a stage gate before the next one unless the stated policy allows auto-advance. Given a ticket key rather than a change ID, it points at `/lbvs-aidlc-ticket` instead of guessing a slug. Each stage reads the previous artifacts rather than relying on a long chat transcript. You can also invoke any stage skill directly, and Claude may load a stage skill when your request matches its `when_to_use` triggers; either way the same gate applies. Revise earlier decisions when new information appears: update the affected files and make the change visible.

### Stage gates and the flow policy

At the end of every stage the skill summarises the artifact path, decisions taken, open questions and checks run with their results. What happens next depends on the **flow policy**, which the orchestrator states once per run, verbatim, in the conversation:

- `Flow policy: confirm each stage` — the default, and what every skill assumes when no policy was stated.
- `Flow policy: auto-advance when clear, stop before build`
- `Flow policy: auto-advance when clear, including build`

A stage may auto-advance only when **all** of these hold: the stated policy is an auto-advance one; the artifact was saved *and* read back in this run; it records no open questions, unresolved decisions or missing inputs; no check failed and no required check is "not run"; no requested CE review is pending; the next stage is not `lbvs-aidlc-build` unless the policy includes build; and the next step is not a commit, push, PR, merge, publication or deployment. The skill then prints one line—`Auto-advancing to <next stage> (policy: <policy>; no open questions, checks: <summary>)`—invokes the next stage skill through the Skill tool with the bare change ID, and says that you can interrupt.

Otherwise it asks with AskUserQuestion, options exactly **Proceed to \<next stage\>**, **Revise this stage**, **Stop here**; after review the options are exactly **Fix findings (build)**, **Re-review at higher effort**, **Open PR (lbvs-aidlc-ship)**, **Capture lesson (lbvs-aidlc-learn)**, **Done**. It always asks when the policy is confirm-each-stage, when any condition above is unmet, at `lbvs-aidlc-review` (the pass always presents its findings and the post-review gate is always asked), when the transition would start implementation under a "stop before build" policy, or when a stage ended read-only or unsaved. The one place an auto-advance policy reaches past review is the review loop below: under `Flow policy: auto-advance when clear, including build`, fix → verify → re-review cycles may continue by themselves up to the three-cycle cap, announcing each hop. `/lbvs-aidlc-fix` keeps every question it already had: the failing-test commit choice and its closing gate are always asked; `/lbvs-aidlc-ship` always asks. A summary is not approval, no gate is ever answered on your behalf, and an auto-advance policy is never assumed or claimed when none was stated. Stage order: intent → design → plan → build → verify → review; the review loop and ship follow.

### Review loop and escalation

Review tiers map to the bundled `/code-review` effort argument: **standard** = `/code-review high`, **escalated** = `/code-review xhigh`, **maximum** = `/code-review max`, **cloud** = `/code-review ultra` (multi-agent cloud review — the skill says it costs more and needs the cloud feature). The first pass runs at standard. After a fix pass, the re-review runs at escalated. `maximum` and `cloud` run only when the engineer selects **Re-review at higher effort** or states it. Severity follows [REVIEW.md](../REVIEW.md): **Important** (must be addressed or explicitly dismissed) versus **nit**.

The loop: review → (Important findings) → fix (`lbvs-aidlc-build` with the agreed finding IDs) → verify → re-review at escalated → … until a pass returns zero Important findings or **three fix cycles** have run. At either end it stops and asks the post-review gate. Findings carry stable IDs (`R1`, `R2` …) that persist across passes; a re-review reassesses those IDs and reports new regressions, and leaves out-of-scope findings marked not rechecked rather than silently resolved. `review.md` records each pass with its tier, findings and disposition (fixed, dismissed with reason, open). A pass with zero open Important findings is the precondition `/lbvs-aidlc-ship` reads from disk; a provider verdict is still not approval.

### Shipping a reviewed change

`/lbvs-aidlc-ship [change-id]` resolves the ID like every other skill, then reads its preconditions from disk rather than from the conversation: the latest pass in `changes/<id>/review.md` has zero open Important findings (otherwise it stops and points back to the review loop), and `evidence.md` or verify evidence is present. It then:

1. Shows `git status` and a diff summary. The branch must be `aidlc/<id>` or confirmed by the user; it refuses to run on the default branch.
2. Delegates the pre-PR conventions check to `lbvs-aidlc-conventions-checker` with the change ID and shows its `K<n>` findings and commands table in the summary ([below](#pre-pr-conventions-check)). The report stays in the conversation; nothing is written to `review.md` or `evidence.md`.
3. Asks one AskUserQuestion, whatever the flow policy. With zero open Important K-findings the options are exactly **Commit, push and open PR**, **Commit only**, **Stop here**; with any Important K-finding they are exactly **Fix findings first (lbvs-aidlc-build)**, **Ship anyway: commit, push and open PR**, **Stop here**.
4. Commits with a Jira-key title when the ID starts with one (`VS-1234: <imperative title>`), otherwise a Conventional Commit type; the body says why and ends with `Change: <id>`. The `changes/<id>/` artifacts are committed with the code.
5. Pushes `aidlc/<id>` to `origin` only after the explicit choice — never to the default branch, never with force.
6. Opens the PR with `gh pr create --base <default branch> --title … --body-file <rendered template>`, or through the github MCP when `gh` is absent. The body comes from the skill's bundled `templates/pr-body.md`: Summary (from intent), Ticket link, Spec/plan links, Evidence (verification summary from `evidence.md`/verify), Review (passes, tiers, findings closed; when shipped anyway, the accepted K-findings), Knowledge records (ADR/incident/threat-model paths, if any), Checklist (conventions run, tests, no secrets). It never merges, approves, enables auto-merge or edits branch protection.
7. Reads the PR URL back and records it under References in `evidence.md`/`review.md`.

Pipelines, image promotion and environment approval holds remain the platform's and a human's; `/lbvs-aidlc-ship` ends at the open PR ([deferred delivery](../FUTURE_WORK.md#f4--delivery-integration-through-circleci)).

#### Pre-PR conventions check

`lbvs-aidlc-conventions-checker` (Read, Glob, Grep, Bash) is the sixth bundled agent and the only one besides the verifier that runs commands — and it runs only the ones the repository documents. Inputs: the change ID; `docs/repo-profile.md` (fallback: `CLAUDE.md`, `CONVENTIONS.md`, `.pre-commit-config.yaml`, `.editorconfig`); `git diff <default-branch>...HEAD` plus uncommitted changes; `changes/<id>/spec.md` and `plan.md`; the glossary named in the profile. Four passes: (1) run the lint/format/test commands verbatim from the profile's Commands section (or `CLAUDE.md` Commands) — never inventing or modifying a command, never `--fix` — and record `command | exit | one-line summary`; (2) diff versus conventions: naming and layout, hand edits under the profile's Generated paths, files outside the plan's scope, credential-looking strings, large binaries; (3) delivery hygiene: branch `aidlc/<id>`, commit titles matching the profile's format (Jira key `VS-1234:` when the ID starts with one), `changes/<id>/` artifacts present, an ADR when the diff changes a boundary, contract or technology (a finding, not a blocker); (4) glossary drift: a domain term introduced in code or docs that the glossary lacks is a nit "new term". Output: `**Checker:** lbvs-aidlc-conventions-checker`, findings `K1..` with severity Important | nit, `file:line` and the smallest fix, the commands table and `Not examined:`. It is advisory — it never edits, commits or fixes — and its K-findings are input to the ship question, not a blocker; [REVIEW.md](../REVIEW.md) treats them the same way. Adapted from the awslabs/aidlc-workflows quality agents (MIT-0) and ECC's `code-reviewer` (MIT); the agent file names the exact upstream files.

### Change IDs you do not have to remember

A change ID still matches `^[a-z0-9]+(-[a-z0-9]+)*$`, so a ticket key fits as a lowercase prefix: `vs-1234-order-export`. You rarely need to type one:

- `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" status` lists every `changes/<id>/` with which stage artifacts exist (intent, spec, plan, evidence, review), the stage reached, the next stage, the handoff count and a marker on the change currently in play. A present file is not proof that its stage is finished.
- `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" current` prints `<change-id>\t<source>` and exits 1 when nothing resolves. Resolution order: the branch name (`aidlc/<id>`, `aidlc+<id>`, `worktree-aidlc/<id>`, `worktree-aidlc+<id>`), then `.aidlc/current`, then the only change without `review.md`.
- `.aidlc/current` is a machine-local pointer, ignored by Git and never exported or carried by a handoff. The orchestrator writes the resolved ID there so a later session in the same checkout finds it.

Every ID-taking skill follows the same rule: a valid ID in the argument wins; an empty argument falls back to `current`, and the skill says which source it used; an argument carrying extra prose contributes only a leading valid token, with the rest treated as context. When nothing resolves the skill asks, proposing a slug derived from your actual request and prefixed with the ticket key when one is known—it never invents a ticket key, and never creates `changes/<id>/` from an unresolved ID. Two exceptions: `/lbvs-aidlc-ideate` takes a topic ID, has no `current` fallback and asks when the topic is absent; `/lbvs-aidlc-ticket` takes the ticket key or issue URL itself, derives `<key-lowercase>-<slug>` (≤ 40 characters, same regex) from the fetched record, confirms it with you and only then writes `.aidlc/current`.

### Project mode and onboarding

`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" mode` prints exactly one line, `AIDLC project mode: greenfield` or `AIDLC project mode: brownfield`, followed by ` — <reasons>`; a `.aidlc/mode` file containing `greenfield` or `brownfield` overrides detection. The `project-mode.sh` SessionStart hook injects that line into every session. For brownfield with no repository `CLAUDE.md`/conventions record, `/lbvs-aidlc` invokes `lbvs-aidlc-onboard` before intent: the read-only `lbvs-aidlc-repo-scout` agent (Read, Glob, Grep) returns a conventions report—stack, layout, build/test/lint commands, naming, error handling, test patterns, hotspots, existing agent instructions, risks—and a draft of `docs/repo-profile.md` from the bundled [profile template](../.claude/skills/lbvs-aidlc-onboard/templates/repo-profile.md) ([repository context](#repository-context)); then you choose **Modernize (adopt current patterns)**, **Stay legacy (inherit existing style)** or **Decide later**. Legacy invokes the existing `inherit-legacy-style` skill; modernize recommends the `code-modernization` plugin and relevant pattern skills without installing them. The skill then proposes a repository `CLAUDE.md` (≤60 lines, with a "Things Claude gets wrong here" section) and path-scoped `.claude/rules/` drafts, recommending `/init` with `CLAUDE_CODE_NEW_INIT=1` as the alternative, and writes them, the profile, `.aidlc/mode` and `docs/onboarding.md` only on explicit confirmation. Rerunning it refreshes a profile that `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" profile` reports stale.

Onboarding also runs `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" conventions` (report only) and records the repository's existing tooling in the `CLAUDE.md` draft; it never overwrites a convention file. In a **greenfield** repository it offers (AskUserQuestion) **Adopt default conventions (`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" conventions --apply`)** and, when the project needs cloud delivery, points at [`docs/platform/README.md`](platform/README.md) — the `Logicbroker/app-template` route, whose `AGENT-SETUP.md` is fetched with an authenticated `gh api` because the repository is internal. See [platform and conventions](#platform-and-conventions).

### Repository setup with `/lbvs-aidlc-init`

`/lbvs-aidlc-init` (no argument; triggers "set up aidlc", "initialise this repo", "adopt aidlc here", "brownfield setup", "init", "first time in this repository") is the idempotent, report-first wizard for adopting the package in a repository. Every step reports what it found and ends with an AskUserQuestion wherever it would write; every write is read back; a rerun finds its earlier results and moves on. It never installs plugins, changes settings, stores secrets, commits or pushes.

0. **Doctor** — `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" doctor`: required and optional tools, MCP auth state per server; offer **Run `doctor --install`** / **Skip**.
1. **Mode** — `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" mode`. Brownfield invokes `lbvs-aidlc-onboard` (above) and keeps its scout report; greenfield offers **Adopt default conventions (`conventions --apply`)** and points at [`docs/platform/README.md`](platform/README.md) when cloud delivery is needed.
2. **Platform facts** — when [`docs/platform/platform.md`](platform/platform.md) still holds bracketed template items, fill only what `.circleci/config.yml`, `deploy/`, `catalog-info.yaml` or `Taskfile.yml` reveal read-only, leaving unknowns bracketed; write on confirmation.
3. **MCP and CE** — from the doctor output, what still needs authentication (`atlassian` → `/mcp`; `github` → `GITHUB_PERSONAL_ACCESS_TOKEN`; `context7` optional) and whether `compound-engineering:*` skills are in the session catalog, giving the install command for the engineer to run.
4. **Code graph** — with `graphify` installed and no `graphify-out/graph.json`, offer **Run `/graphify .`**.
5. **Agent maker** — from the scout report or the repository layout, propose at most three repository-specific candidates, each with name, description, tools, the stage that delegates to it and why none of `lbvs-aidlc-verifier`, `lbvs-aidlc-repo-scout`, `lbvs-aidlc-design-reviewer`, `lbvs-aidlc-threat-modeler`, `lbvs-aidlc-test-critic`, `lbvs-aidlc-conventions-checker` or the bundled Explore/Plan subagents already covers it. Heuristics: a large or vocabulary-heavy subsystem (≥ 40 files, or its own glossary/docs) → read-only `<repo>-<area>-scout`; a documented multi-step test/build/verify procedure → Bash-capable `<repo>-checker` that runs only those commands and reports; generated code with its generator present → read-only `<repo>-generated-guardian` that flags hand edits under generated paths; a recurring documented procedure (release, migration, data fix) → a repository skill, not an agent — and a `docs/playbooks/` entry with Runs ≥ 3 and `Status: Verified` is proposed here as `.claude/skills/<repo>-<playbook>/SKILL.md`. Accepted agents are drafted from the bundled `templates/agent.md` into `.claude/agents/<name>.md` (body ≤ 3 KB, one-sentence description — plugin agents cost startup context) and written only on confirmation. Alternatives named once: `/init` with `CLAUDE_CODE_NEW_INIT=1` (proposes CLAUDE.md, skills and hooks) and the official `skill-creator` and `plugin-dev` plugins.
6. **Ignore patterns** — check `.gitignore` for `.claude/worktrees/`, `.aidlc/fix/`, `.aidlc/current` and `.codegraph/`; offer to append the missing lines.
7. **Summary** — Written / Recommended / Skipped, then **Start a change (/lbvs-aidlc)** / **Start from a ticket (/lbvs-aidlc-ticket)** / **Done**.

Existing `CLAUDE.md`, `AGENTS.md`, rules, `platform.md` content and `.gitignore` entries stay authoritative — the wizard adds, never rewrites — and a drafted agent inherits the repository's permissions and nothing more.

### Worktrees

Every new change or bug fix should run in its own worktree. Step 0 of `/lbvs-aidlc` and `/lbvs-aidlc-fix` proposes one and asks before creating it; if a worktree for this change already exists, it is entered rather than duplicated. In Claude Code the route is the EnterWorktree tool with the name `aidlc/<change-id>`. This project registers a `WorktreeCreate` hook (`.claude/hooks/worktree-create.sh` → `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" worktree`) that replaces the host's default naming, so the result is the directory `.claude/worktrees/aidlc+<change-id>` on branch exactly `aidlc/<change-id>`, branched from local `HEAD`. Because a `WorktreeCreate` hook replaces the default behaviour, the hook also honours `.worktreeinclude` itself and copies `.env` and `.claude/settings.local.json` into the new tree. A name that is not `aidlc/<something>` keeps the ordinary `worktree-<name>` branch; an existing worktree directory is reused; a missing or unusable name fails the hook, and the worktree creation fails with it rather than falling back to a generic name.

The hook leaves no host-side worktree marker, so Claude Code's own worktree sweep does not manage these directories: remove one yourself with `git worktree remove .claude/worktrees/aidlc+<change-id>` when the change is done. Where the tool or the hook is unavailable, `git worktree add ../<repo>-<change-id> -b aidlc/<change-id>` remains the documented fallback, and the `.worktreeinclude` files must be copied by hand.

## Files per change

Use `changes/<change-id>/` with `intent.md`, `spec.md`, `plan.md` and, when useful, `review.md`; bug fixes add `evidence.md`; a spike adds `spike.md` before or instead of the rest. Optional immutable continuity snapshots live under `changes/<change-id>/handoffs/`; they supplement these working artifacts rather than replacing them. The helper creates only the initial draft:

```sh
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" new example-change
```

Replace the ID with the real change; a ticket key can prefix it (`vs-1234-order-export`). Use lowercase letters/digits separated by single hyphens. `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" status` shows which changes already exist and how far each one got. Templates are starting instructions, not completed work. Do not invent facts to fill them. See [artifact conventions](ARTIFACTS.md).

## Repository context

Stages stop re-reading the repository's conventions on every run. Before scouting or asking, a stage reads, when present and in this order:

1. **`docs/repo-profile.md`** — the committed facts about the repository: header lines `# Repository profile: <repository>`, `Last verified: <YYYY-MM-DD> at <full commit sha>`, `Manifests: <space-separated repo-relative paths>` (e.g. `pyproject.toml package.json .pre-commit-config.yaml .circleci/config.yml`), `Profiled by: lbvs-aidlc-repo-scout via /lbvs-aidlc-onboard | /lbvs-aidlc-init`; then Identity (company **Logicbroker** or **Virtualstock**, the glossary file, `docs/platform/platform.md`, the service/catalog name), Stack, Layout (directory → purpose), Commands (build/test/lint/format/run verbatim with their source path), Conventions (formatter, linter, pre-commit, commit-title format, branch naming, PR template), Testing (framework, layout, fixtures, how to run one test), Generated paths (never hand-edit; generator command), Hotspots and risks, Ownership (CODEOWNERS/teams), Existing agent instructions (`CLAUDE.md`, `AGENTS.md`, rules, cursorrules), Playbooks (links) and Open questions. `lbvs-aidlc-repo-scout` drafts it from the bundled [profile template](../.claude/skills/lbvs-aidlc-onboard/templates/repo-profile.md) during `/lbvs-aidlc-onboard` or `/lbvs-aidlc-init`, and it is written only on confirmation and read back. Check freshness first with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" profile`, which parses only the header lines and prints `profile: missing|fresh|stale (<n> manifest commits since <rev>)` — stale means a listed manifest changed since the recorded commit, so the affected sections are re-scouted; missing means scout as before and offer to write the profile.
2. **The company glossary** under [`docs/glossary/`](glossary/README.md), the file named in the profile's Identity section — [`logicbroker-glossary.md`](glossary/logicbroker-glossary.md) or [`virtualstock-glossary.md`](glossary/virtualstock-glossary.md). Use its terms verbatim in intent, spec, plan, code identifiers and docs. A domain term the glossary lacks is flagged as a **new term** and offered as a glossary entry (from [`docs/glossary/template.md`](glossary/template.md)), never silently coined; the [comparison](glossary/logicbroker-glossary-comparison.md) records where the two companies' vocabularies differ.
3. **[`docs/playbooks/README.md`](playbooks/README.md)** — the index of recorded procedures (`| Playbook | Trigger | Status | Runs | Last verified |`). When a playbook's Trigger matches the work, `lbvs-aidlc-plan` cites it in the task and `lbvs-aidlc-build` follows it step by step, verifying each step as it says, and on confirmation bumps its Runs with the change ID. A spike whose answer is a repeatable procedure of ≥ 3 ordered steps, or a procedural lesson at `/lbvs-aidlc-learn`, ends by offering to record one from [`docs/playbooks/template.md`](playbooks/template.md) (`Status: Draft | Verified | Superseded by <path>`, `Last verified: <YYYY-MM-DD> at <revision or environment>`, `Runs: <count> (<change IDs>)`, Trigger, Preconditions, numbered Steps each ending with how to verify it worked, Verification, Rollback, Pitfalls linking `docs/solutions/` lessons, Sources, Promotion). A run that passes the playbook's Verification section marks it Verified; Runs ≥ 3 and Verified makes the playbook a candidate repository skill `.claude/skills/<repo>-<playbook>/SKILL.md`, proposed via `/lbvs-aidlc-init` step 5 and never auto-written. Playbooks hold procedures; lessons hold one insight; ADRs hold decisions; rules hold recurring corrections.
4. **[`docs/platform/platform.md`](platform/platform.md)** and **[`docs/references/libraries.md`](references/libraries.md)** as before.

Only what is missing or stale is then scouted, and only what the artifacts still need is asked. Each stage skill carries this as one sentence — "Repository context: read per ${CLAUDE_PLUGIN_ROOT}/docs/WORKFLOW.md#repository-context before scouting; scout only what is missing or stale." — rather than repeating the list. The profile, glossary and playbooks are facts and procedures the next session reads, not rules or permissions: a fact that contradicts the code is corrected in the profile through a reviewed change, and the profile is refreshed by rerunning `/lbvs-aidlc-onboard`. The pre-PR [conventions check](#pre-pr-conventions-check) reads the same profile and glossary, so a stale profile shows up there as well.

## Skills, agents and hooks

`/lbvs-aidlc [change-id]` orchestrates. The stage skills `lbvs-aidlc-intent`, `lbvs-aidlc-design`, `lbvs-aidlc-plan`, `lbvs-aidlc-build`, `lbvs-aidlc-verify`, `lbvs-aidlc-review`, plus `lbvs-aidlc-init`, `lbvs-aidlc-fix`, `lbvs-aidlc-onboard`, `lbvs-aidlc-learn`, `lbvs-aidlc-ticket`, `lbvs-aidlc-spike` and `lbvs-aidlc-ship`, are model-invocable and user-invocable: invoke `/lbvs-aidlc-<stage> [change-id]` directly or let Claude load one when your request matches its triggers ("set up aidlc", "first time in this repository", "start from ticket", "pick up VS-1234", "spike", "feasibility", "how does X work before we decide", "open a PR", "ship it", "ready for review", "create the pull request"). Three utilities are manual-only (`disable-model-invocation: true`): `/lbvs-aidlc-handoff <change-id>` saves a requested continuity snapshot; `/lbvs-aidlc-resume <change-id>` orients without starting work; `/lbvs-aidlc-ideate <topic-id>` compares directions before a change is selected. Two imported skills are wired into the loop and kept at upstream text plus one integration paragraph: `architecture-decision-records` (ECC) writes `docs/adr/NNNN-short-title.md` and its index row after confirmation, and `doc-coauthoring` (anthropics/skills) structures the drafting of intent, spec and knowledge documents without owning any file. That makes 17 `lbvs-aidlc*` commands. See [practical usage recipes](USAGE.md) and [bundled skills and plugins by stage](PLUGINS.md).

Skills are project-scoped bundles under `.claude/skills/`, with templates and references read on demand; shared docs and the helper stay at their repository locations, so copying one skill does not install its dependencies. Six subagents live under `.claude/agents/`, each with an `.omp/agents/<name>.md` counterpart that defers to the Claude definition (tools lowercase): `lbvs-aidlc-verifier` (Bash-capable fresh check), four read-only agents (Read, Glob, Grep) — `lbvs-aidlc-repo-scout` (conventions report and the `docs/repo-profile.md` draft), `lbvs-aidlc-design-reviewer`, `lbvs-aidlc-threat-modeler` and `lbvs-aidlc-test-critic` — and `lbvs-aidlc-conventions-checker` (Read, Glob, Grep, Bash; runs only the commands the profile or `CLAUDE.md` documents, [pre-PR check](#pre-pr-conventions-check)). The design reviewer reads `spec.md`/`plan.md` adversarially against intent, ADRs, `platform.md` and conventions over a bounded pass list (requirements coverage and EARS quality, design consistency with ADRs, platform fit, NFR gaps, missing threat model) and returns **READY** or **NOT READY** with numbered findings and evidence; `lbvs-aidlc-design` invokes it before asking the design gate and reports the verdict as one summary input, never as approval (adapted from awslabs/aidlc-workflows' architecture-reviewer agent, MIT-0). The threat modeler produces a STRIDE table for a named boundary using `docs/security/threat-model-template.md`, with an explicit do-not-flag list — test fixtures, accepted risks documented in `docs/security/`, framework-handled CSRF/escaping when verified; it runs only when a threat-model offer is accepted (adapted from the AWS devsecops agent, MIT-0, and ECC's security-reviewer false-positive list, MIT). The test critic reads a change's tests fresh against the spec's R-IDs — a coverage table `R-ID | test | asserts observable outcome? | gap`, implementation-coupled or tautological tests and over-mocking, missing failure/boundary/concurrency cases named in EARS `IF`/`WHILE` lines, flaky patterns (sleep, wall clock, network, order dependence, shared state) and, for a fix, whether the reproduction test exists, stayed protected and failed pre-fix per `evidence.md` — and returns numbered `C<n>` findings (Important | nit) with the smallest fix and a "Not examined" list; `lbvs-aidlc-verify` offers the delegation once its R-ID map exists, `lbvs-aidlc-review` lists the findings in its context packet, and the verdict is advisory (idea adapted from ECC's pr-test-analyzer, MIT). The conventions checker returns `K<n>` findings the same way to `/lbvs-aidlc-ship`. Repository-specific agents proposed by `/lbvs-aidlc-init` sit beside these under the adopting repository's `.claude/agents/`. Four hooks are registered in `.claude/settings.json`: `check-package.sh` (SessionStart, read-only package check), `project-mode.sh` (SessionStart, injects the project-mode line), `protect-tests.sh` (PreToolUse on `Edit|Write|MultiEdit|NotebookEdit`, denies edits to any path listed in `.aidlc/fix/*.json` while the marker exists) and `worktree-create.sh` (WorktreeCreate, names the worktree and branch as above). The helper behind them exposes `check`, `doctor [--install]`, `mode`, `status`, `current`, `conventions [--apply]`, `profile`, `worktree`, `package` and `new` ([helper reference](REFERENCE.md#helper)). Hooks are deterministic guardrails for this loop, not approval or security enforcement. Shared instructions live in `AGENTS.md`; `CLAUDE.md` imports it with `@AGENTS.md` and adds a Claude-specific section, and `.omp/AGENTS.md` imports `@../AGENTS.md` for Oh My Pi.

Pass at most one validated ID as the slash-command argument—a change ID, except ideation's topic ID and ticket intake's ticket key—and leave it empty when the workflow can resolve it as described above. Discuss task/context, the flow policy, source selection and CE choice in conversation rather than appending them to the argument. In a read-only session, return proposed content; save only through the normal authorised writable workflow. Plan mode does not authorise implementation or a potentially-writing upstream call.

Standalone planning is supported for an already-understood engineering task. State which artifacts are absent; do not fabricate them or pretend the whole chain has been followed.

## Bug-fix evidence loop

`/lbvs-aidlc-fix <change-id>` follows the playbook's failing-test-first rule:

1. Propose the worktree (above), then reproduce the bug.
2. Write a failing test and ask the user to authorise committing it as `test(<change-id>): reproduce <summary>`.
3. Write the marker `.aidlc/fix/<change-id>.json` — `{"change_id": "...", "protected": ["<test path>", ...]}`. While it exists, `protect-tests.sh` denies edits to those paths, so the fix cannot rewrite its own proof.
4. Implement the fix — Context7 first when the fix touches a library API — then run the test, and `/verify` when an app runtime exists.
5. Write `changes/<change-id>/evidence.md` from `.claude/skills/lbvs-aidlc-fix/templates/evidence.md`: Change ID, Summary, References (Jira key/URL, PR URL, incident/alert link — optional, never invented), the EARS triad — **Current** (`WHEN <event> THE <system> <observed wrong behaviour>`), **Expected** (`WHEN <event> THE <system> SHALL <response>`), **Unchanged** (`THE <system> SHALL CONTINUE TO <behaviour>`) — that the reproduction test and the regression checks map to, Reproduction (steps, failing test path, pre-fix output), Fix (files, root cause), Verification (commands and actual output, `/verify` observations, screenshot/recording paths), Regression protection (test kept, eval seed suggestion), Lesson link (`docs/solutions/...` or "none"), Limits.
6. When the symptom arrived through an alert or incident link, offer (AskUserQuestion) to create `docs/incidents/YYYY-MM-DD-<slug>.md` from `docs/incidents/template.md`, add its row to `docs/incidents/README.md` and link it from the evidence References. For a security defect, offer a `docs/security/findings/YYYY-MM-DD-<source>.md` record the same way. Declining is normal; nothing is written unasked.
7. Delete the marker and offer `/lbvs-aidlc-learn <change-id>`; `/lbvs-aidlc-ship` later reads the evidence as its precondition.

`.aidlc/fix/` is ignored by Git. The evidence file is the artifact review and future incidents read; it never claims a check that did not run.

## Knowledge stores

Five plain-Markdown stores keep what the loop learns; a playbooks store keeps proven procedures and a platform pointer layer sits beside them. Each store is written only after an explicit confirmation and a Read-back of the saved file, holds one topic per file, and is guidance the next session reads — not a control, approval or rule:

- **Decisions** — `docs/adr/NNNN-short-title.md` from [`docs/adr/template.md`](adr/template.md), one row per record in [`docs/adr/README.md`](adr/README.md). Supersede, never renumber or delete. Offered by `lbvs-aidlc-design` when a spec introduces or changes an architectural boundary, technology choice or contract, and by `lbvs-aidlc-spike` at its end gate; written by the `architecture-decision-records` skill; an architectural change without one is an `lbvs-aidlc-review` finding.
- **Incidents** — `docs/incidents/YYYY-MM-DD-short-title.md` from [`docs/incidents/template.md`](incidents/template.md), indexed in [`docs/incidents/README.md`](incidents/README.md): evidence, human triage, authorised actions and verified outcome. Offered by `lbvs-aidlc-fix`; linked from `evidence.md`. The live channel or ticket stays the authoritative timeline.
- **Security** — `docs/security/threat-models/<name>.md` from [`docs/security/threat-model-template.md`](security/threat-model-template.md) (offered by `lbvs-aidlc-design` for a new external interface, data store, credential or trust boundary) and `docs/security/findings/YYYY-MM-DD-<source>.md` for `/security-review`, advisory or scan results with their triage; rows in [`docs/security/README.md`](security/README.md).
- **References** — one row per library in [`docs/references/libraries.md`](references/libraries.md) (rules in [`docs/references/README.md`](references/README.md)): Library, Context7 ID exactly as resolved, version the repository uses, pages that answered real questions, gotchas dated with the change ID. Added or updated by design, plan, build and fix within the same change whenever a [Context7 lookup](#current-documentation-first) settled a real question; rows for libraries no longer used are deleted.
- **Lessons** — `<root>/solutions/<category>/<topic>.md` through `/lbvs-aidlc-learn` ([below](#capture-one-non-obvious-lesson)). The template carries `Status: Verified | Needs re-check | Superseded by <path>`, `Last verified: <date> against <revision or environment>`, `Confidence: 0.3 (1–2 observations) | 0.5 (3–5) | 0.7 (6–10) | 0.85 (11+)`, `Observations: <count, change IDs>` and `Scope: project | team`; a lesson whose evidence has aged is marked, not left to mislead, and a re-observed topic bumps the existing lesson's Observations/Confidence instead of gaining a duplicate.
- **Playbooks (procedure store)** — `docs/playbooks/<kebab-title>.md` from [`docs/playbooks/template.md`](playbooks/template.md), one row per playbook in [`docs/playbooks/README.md`](playbooks/README.md) (`| Playbook | Trigger | Status | Runs | Last verified |`). Written by `lbvs-aidlc-spike` (**Save as playbook**) and `lbvs-aidlc-learn` (**Save as playbook instead**) when a spike or lesson proved a repeatable multi-step procedure; read per [repository context](#repository-context) before scouting; cited by plan, followed by build, which bumps Runs on confirmation; Runs ≥ 3 and Verified is the promotion threshold to a repository skill proposed through `/lbvs-aidlc-init`. Playbooks hold procedures; lessons hold one insight; ADRs hold decisions; rules hold recurring corrections.
- **Platform (pointer layer)** — [`docs/platform/platform.md`](platform/platform.md), filled once per adopting service from [`docs/platform/README.md`](platform/README.md): environments and promotion path, orb pin and jobs, observability identity, secrets/identity stores, catalog metadata and deployment authority. Read by design and plan; a new data store, queue or integration requires an entry. Not a record of decisions — those go to an ADR.

Knowledge versus rule: **a correction that keeps recurring becomes a rule** in `AGENTS.md` or a path-scoped `.claude/rules/` file through review; a record captures a decision, an event or a verified lesson with its evidence and freshness. The promotion rule makes that concrete: a lesson observed in **≥2 changes with confidence ≥0.8** is a candidate rule for `AGENTS.md`/`.claude/rules/`, proposed to the engineer and never auto-written. The confidence ladder, observation count and promotion threshold borrow the record schema of ECC's `continuous-learning-v2` (MIT); its Pre/PostToolUse observation hooks, the `nohup` observer daemon that spawns background `claude --model haiku` calls, and the telemetry-like `observations.jsonl` log of tool inputs/outputs were deliberately **not** imported — the observer is off by default upstream, the model calls are billed to the engineer without a per-run choice, and the log lives outside the repository where review cannot see it. Records are read at equal weight, so prune or supersede stale ones. This model is adapted from the team-knowledge chapter of AWS's [aidlc-workflows](https://github.com/awslabs/aidlc-workflows/blob/main/docs/harness-engineering/07-team-knowledge.md) and from the ADR template shape of the sibling Logicbroker `shared-services-aidlc` repository, in our own words. The automation that would feed these stores from hosted scans, monitoring or incident channels stays [deferred](../FUTURE_WORK.md#f5--maintenance-and-operational-feedback).

## Traceability from requirement to check

Acceptance criteria, tasks and verification share one ID space so review can see what is covered. The shapes are borrowed from [Kiro specs](https://kiro.dev/docs/specs/) (requirements → design → tasks with EARS criteria and requirement trace lines); the tooling — run-all task waves, property generation, spec hooks — is not.

- **spec.md** lists acceptance criteria as EARS lines with stable IDs `R<n>.<m>`: `WHEN <event> THE <system> SHALL <response>`, `IF <condition> THEN THE <system> SHALL <response>`, `WHILE <state> THE <system> SHALL <response>`, the ubiquitous `THE <system> SHALL <response>`, and for bug fixes `THE <system> SHALL CONTINUE TO <unchanged behaviour>`. IDs are never renumbered once a task refers to them; a withdrawn criterion is struck through with a reason.
- **plan.md** lists numbered checkbox tasks `- [ ] T1.2 …`, each ending `_Requirements: R1.1, R2.3_` and carrying `depends on: T1.1` where order matters. `lbvs-aidlc-plan` checks that every R-ID appears in at least one task or names the exclusion.
- **build** takes one task at a time, in order or the task the engineer names, with spec and plan in context; it runs that task's own check and ticks `[x]` only after the check passed — never ahead, never for a task whose check did not run.
- **verify** reports a table `R-ID | check | observed result | not run (reason)`, so an uncovered requirement is visible as a row, not hidden behind a green command; on request it delegates to `lbvs-aidlc-test-critic`, whose `R-ID | test | asserts observable outcome? | gap` table and `C<n>` findings show where a green test would still let the described behaviour be wrong — input to review, not a second verdict.
- **evidence.md** (fix) states the EARS triad Current / Expected / Unchanged; the reproduction test maps to Expected and the protected regression tests to the `SHALL CONTINUE TO` lines.

## Current documentation first

Before designing, planning, implementing or fixing against a library, framework, SDK or cloud API, resolve its current documentation: the `context7` MCP (`resolve-library-id`, then `query-docs`) declared in `.mcp.json`, or the imported `documentation-lookup` skill. Training data is not a source for API signatures, configuration keys or version behaviour. The artifact cites the Context7 ID and the repository's pinned version of the library; when the lookup settled a real question, the same change adds or updates the row in [`docs/references/libraries.md`](references/libraries.md). If Context7 is unavailable, the skill says so and cites the official documentation URL instead — it does not fall back silently.

## Platform and conventions

The package is generic; the company's cloud platform is pointed at, not copied. [`docs/platform/README.md`](platform/README.md) names the two internal repositories — `Logicbroker/app-template` (GitHub template with `AGENT-SETUP.md`, platform capabilities, operations and integrations guides) and `Logicbroker/app-delivery-kit` (the public CircleCI orb `lb-pipelines/app-delivery-kit-vs@1` and the `central-app` Helm chart) — and what each adopting repository records in its own [`platform.md`](platform/platform.md). Both repositories are internal: fetch files with an authenticated `gh api …/contents/<path>`; plain raw links 404. `lbvs-aidlc-design` and `lbvs-aidlc-plan` read `platform.md` when present and express deployment, observability and promotion changes as values files and pipeline config for the orb, never hand-rolled infrastructure; a new data store, queue or integration requires a `platform.md` entry and a threat-model offer. Running pipelines and promoting images remain [deferred](../FUTURE_WORK.md#f4--delivery-integration-through-circleci); the stages prepare reviewable configuration, `/lbvs-aidlc-ship` opens the PR, and a human triggers delivery.

Conventions follow the same rule. [`templates/conventions/`](../templates/conventions/CONVENTIONS.md) holds the defaults (`.editorconfig`, `.pre-commit-config.yaml` with gitleaks, `ruff.toml`, `biome.json`, `CONVENTIONS.md` — branch, commit-title and PR rules that `/lbvs-aidlc-ship` follows). `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" conventions` reports, per file, whether the repository already owns that concern (an existing `pyproject.toml`, ESLint/Prettier config, lefthook or `CONTRIBUTING.md` counts) or a default is available; `conventions --apply` copies only the missing defaults and never overwrites. Greenfield adopts when the engineer accepts the onboarding offer; brownfield keeps its own, recorded by `lbvs-aidlc-onboard` in the repository `CLAUDE.md` and in the Conventions and Commands sections of `docs/repo-profile.md` ([repository context](#repository-context)). `lbvs-aidlc-build` runs the repository's pre-commit/lint before declaring a task done, and `lbvs-aidlc-conventions-checker` reruns the documented commands and compares the whole diff with the recorded conventions before `/lbvs-aidlc-ship` asks its question ([pre-PR check](#pre-pr-conventions-check)). Changing a default is an ADR.

## Saving a plan before implementation

`lbvs-aidlc-plan` produces the complete proposal read-only, naming its exact source when it exists. A native host-managed plan file is machine-local scratch, not the canonical plan. After the engineer confirms the proposal and makes the normal writable transition, `lbvs-aidlc-build` owns saving it to `changes/<change-id>/plan.md`.

State **save only** or **save and implement** in the conversation; the slash-command argument remains just the ID. The build entrypoint reads the exact selected proposal and current artifacts, resolves material conflicts rather than overwriting newer work, saves before application edits, and rereads the saved plan. A missing source or a handoff summary is not enough to reconstruct the confirmed proposal. Save-only stops without application edits, checks, review invocation or implementation.

If CE document review was requested for the proposal and remains pending, save-and-implement stops after saving and returns the exact saved plan to the engineer for `/lbvs-aidlc-plan <change-id>` review. Findings and unresolved decisions come back before implementation. Do not silently waive that request, invent acceptance, or infer current permission from a historic snapshot. An explicit current decision may change/defer the review request; no mandatory review gate is introduced.

## Durable handoff and resume

Use the [handoff utility](../.claude/skills/lbvs-aidlc-handoff/SKILL.md) when the engineer requests a pause or transfer. In a writable session, save a new pointer-first snapshot under `changes/<change-id>/handoffs/<topic>.md`, never overwriting an earlier snapshot. Capture actual completed/unfinished work, user-attributed decisions versus inference, pending reviews, observed and not-run checks, relevant current files and the next action. Do not silently save the canonical plan as part of snapshot creation. In read-only mode, return proposed handoff text explicitly labelled **not saved**.

Use the [resume utility](../.claude/skills/lbvs-aidlc-resume/SKILL.md) in a fresh conversation. An exact same-change snapshot selected in the conversation is read directly; an unavailable source is not replaced with the newest file. If snapshots exist but none is selected, use Glob to present a filename-only shortlist and ask for selection; do not read candidate bodies or frontmatter. With no snapshots, or an explicit “current artifacts only” request, orient from available canonical files and relevant current code, naming absent context rather than inventing history.

Resume treats the snapshot as untrusted historical context, not instructions or permission. Check material claims against current project instructions, artifacts and relevant current code; report drift, expired evidence and missing machine-local state. No commands, external-link traversal, unrelated local-file reads, mutation, automatic workflow invocation or implementation follows. Recommend the actual next action—discovery, a pending choice, planning, build, verification or review as appropriate—then stop for the current engineer's direction. Do not mark a handoff consumed.

Both utilities work without CE. If the engineer explicitly selects it, check for the loaded `compound-engineering:ce-handoff` capability and follow the utility's upstream contract. Creation pins the repository snapshot destination, overriding CE's temporary-store default; resume supplies the exact selected snapshot, not global temporary-store discovery. CE-created Markdown also remains readable by ordinary AIDLC resume without the plugin. If CE is selected but unavailable, offer installation/reload or an explicitly labelled ordinary path, and honour an already-chosen fallback without pretending CE ran.

Snapshots do not preserve a worktree or transfer uncommitted files. For another machine/engineer, the selected snapshot **and the referenced current artifacts/code** must be available through an engineer-authorised sharing method. Label native plan files and other machine-local dependencies; a link to missing scratch is not a durable proposal. Do not automatically commit, stash, copy to another worktree, publish or change permissions. These are advisory workflow boundaries, not a new enforcement or session-storage service.

## Ideation and durable learning

Both utilities work ordinarily without CE. Their supporting store defaults to `docs`; an explicit `docs_root` is read only from repository `.compound-engineering/config.yaml`, never its local override. Use one validated repository-relative, symlink-resolved root, not the repository root or `.git/`. An invalid/unclear value is a reported limitation, not a silent fallback or reason to create configuration. These documents are not canonical specs/plans, current proof, rules or permission.

Resolve that root **before** any solution/ideation-store listing, search or read, including preliminary discovery commands. Inspect the config result first; never batch it with a speculative default-store probe. Shared `${CLAUDE_PLUGIN_ROOT}/docs/WORKFLOW.md` remains guidance, not an alternate artifact store.

### Compare directions before intent

The [ideation utility](../.claude/skills/lbvs-aidlc-ideate/SKILL.md) reads relevant repository code/docs and applicable lessons, generates candidates before critique, rejects weaker ideas with reasons and saves a ranked Markdown result under `<root>/ideation/`. A topic ID does not create a change. Use an exact engineer-selected source for refinement; never silently resume the newest file or overwrite a fresh-run collision. Read back the final output before reporting it saved.

Explicit CE selection invokes real `compound-engineering:ce-ideate` with `output:md` and the actual repository focus. Upstream grounding/generation/critique, native subagents and private temporary scratch remain real; no external research, provider switch, pack-resolver execution, publication, browser launch or automatic CE continuation is authorised. CE has no documented return-to-caller flag here; the wrapper's bounded caller continuation is advisory and must be checked, not presented as an upstream API guarantee.

After the engineer selects an idea, manually invoke `/lbvs-aidlc-intent <new-change-id>` with the exact saved source and idea title/number in conversation. Intent reads that source, checks current context and carries provenance, tradeoffs and unknowns without treating ranking or selection as accepted requirements. Ordinary intent remains available; optional brainstorming requires its own explicit selection.

### Capture one non-obvious lesson

The [learning utility](../.claude/skills/lbvs-aidlc-learn/SKILL.md) captures one solved, verified insight under `<root>/solutions/` only when losing its reasoning would plausibly cause recurrence, material risk or substantial rediscovery. Routine work already explained by code/tests/docs and unsupported or unverified solutions are **skipped**, not padded into notes. Preserve observed versus user-reported/historical evidence and limits; capture never reruns project proof. Search relevant existing lessons, skip adequate duplicates, and require explicit direction to update an identified stale same-topic note.

Ordinary capture changes only the learning. Explicit CE capture invokes actual `compound-engineering:ce-compound` with `mode:non-interactive depth:lightweight`. Disclose its update-only maintenance of an **existing root `CONCEPTS.md`** before invocation; if that extra write is forbidden, offer ordinary capture or stop rather than secretly changing the upstream contract. CE's document-only claims/frontmatter checks are not new application verification. No glossary creation, Full-mode history/subagents, rule/global-memory/config updates, automatic refresh or next workflow follows. Read the exact saved learning and any changed glossary after their final writes; report a real skip or incomplete return honestly.

Consult narrowly relevant lessons during later intent/design/planning and check their applicability against current code. ## Review without rebuilding the reviewer

The AIDLC wrapper prepares one same-change packet with concrete intent/spec/plan content, applicable `REVIEW.md` (the repository's own file, else `${CLAUDE_PLUGIN_ROOT}/REVIEW.md`) policy, actual check evidence, prior finding IDs and the real diff scope. [Review options](../.claude/skills/lbvs-aidlc-review/references/review-options.md) defines exact provider recipes and the copyable packet. Include staged, unstaged and relevant untracked content for working-tree review; record resolved revisions/comparison semantics for committed scope. Recheck scope before dispatch and after return.

Invoke an existing reviewer only when the current catalogue exposes a supported mechanism and context channel. Claude's bundled non-cloud review treats trailing arguments as the target, not a free-form brief, and its fork is not guaranteed to inherit parent chat or `REVIEW.md` (the repository's own file, else `${CLAUDE_PLUGIN_ROOT}/REVIEW.md`); the effort argument is what the [tiers](#review-loop-and-escalation) set (`high`, `xhigh`, `max`, `ultra`). Do not invent flags or claim context transfer from preparation alone. Without a supported route, return **prepared — not run**, a separate documented command, the completed packet and the engineer's transfer/menu action. An explicitly selected existing OMP reviewer with custom instructions is another route; do not silently substitute providers or start a hidden session.

Preserve actual native findings, severity/confidence, locations, evidence, verdict and coverage/errors; distinguish wrapper observations. Classify each finding as **Important** or **nit** per `REVIEW.md` (the repository's own file, else `${CLAUDE_PLUGIN_ROOT}/REVIEW.md`) and give it a stable ID that later passes reuse. Unconfirmed artifact/policy coverage is partial, and newer edits make affected coverage stale. No review pass fixes code or runs application/tests. Save `review.md` on request after results return, with actual post-write Read, recording the pass's tier, findings and disposition. A separate authorised fix pass (`lbvs-aidlc-build` with the agreed IDs) addresses selected IDs and reruns affected checks; re-review at the escalated tier explicitly reassesses those IDs while leaving out-of-scope findings not rechecked. After three fix cycles the loop stops and asks regardless of policy. A provider verdict is not approval, remote-posting permission or a clean bill for unreviewed work — it is the precondition `/lbvs-aidlc-ship` checks, and shipping still asks.
