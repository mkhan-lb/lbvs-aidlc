# Artifacts and engineer handoffs

Status: draft

This document says what each file the workflow writes contains and where it lives. The stage order, gates, review loop, evidence loop and every other rule are in [WORKFLOW.md](WORKFLOW.md); this document links to them and does not repeat them. The package adapts the artifact-oriented approach in [Anthropic's AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) to that workflow and borrows the traceability shapes from [Kiro specs](https://kiro.dev/docs/specs/). It does not implement the playbook's whole lifecycle.

Keep a change's canonical artifacts in `changes/<change-id>/`, one directory per change. The ID's shape and how the helper resolves it without being told are in [change IDs](WORKFLOW.md#change-ids-you-do-not-have-to-remember); an unresolved ID is a question for the engineer, never a new `changes/<id>/` directory. External ticket IDs and optional discovery documents are source references, not permission tokens.

For ideation and learning, `<root>` is the supporting artifact root: `docs` unless a valid repository `.compound-engineering/config.yaml` sets `docs_root` ([ideation and durable learning](WORKFLOW.md#ideation-and-durable-learning)). A lesson stays associated with its source change; ideation has a separate topic ID and creates no canonical change artifacts.

Following the [official directory guide](https://code.claude.com/docs/en/claude-directory), active templates live beside the skill that owns them and are read on demand; shared docs stay under `docs/` and `scripts/aidlc.py` stays a shared helper, and all of them travel inside the `lbvs-aidlc` plugin, so copying one skill installs nothing. The knowledge-store templates (`docs/adr/template.md`, `docs/incidents/template.md`, `docs/security/threat-model-template.md`) live beside their indexes rather than in a skill bundle because more than one skill writes to them. Every knowledge record is written only after an explicit confirmation and read back afterwards ([knowledge stores](WORKFLOW.md#knowledge-stores)).

`python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" new <change-id>` creates only the draft intent, substituting the literal `{{change_id}}` and never overwriting ([files per change](WORKFLOW.md#files-per-change)). The ideation utility fills `{{topic_id}}` in its own template. The owning skill creates each later file when the work reaches it; nothing is prefilled as completed work. Replace a template's instructions with actual context and keep real open questions rather than inventing facts.

The helper's other subcommands are listed in [REFERENCE.md](REFERENCE.md#helper); none of them authorises implementation or verifies human approval. Scaffolding an adopting repository with `install`, `sync` and `update` is the [adoption recipe](USAGE.md#11-install-the-plugin-and-scaffold-a-repository).

## Content boundary

`changes/<change-id>/` ships with the code, so the adopting repository's maintainers read it, not the workflow's. Three kinds of content are kept apart:

| Content | Belongs in | Never in the target repository |
| --- | --- | --- |
| What the change is and how it was proven: defect or requirement, decisions and their reasons, what changed, commands and observed results, environment by kind and version (container image, `Python 3.12`, `Django 5.2.14`, an isolated test database), review passes and dispositions, ticket and PR links | `changes/<change-id>/*.md`, the PR body, the repository's existing knowledge store | Nothing |
| How the workflow behaved: host capability gaps, hook or marker behaviour, skill dispatch, package rules, flow-policy history, session restarts, reviewer mechanics | The package repository (`FUTURE_WORK.md`, a package change) or the conversation | Any `changes/<id>/` file or lesson; at most one pointer line under **Limits** ("workflow limitation recorded in the package repository") |
| Machine-local state: absolute paths (`/Users/…`, `/home/…`, `/tmp/…`, `/var/folders/…`, drive letters), session references (`artifact://`, `agent://`, `history://`, `local://`, `xd://`, tool or job names), database or container names of one workstation, quoted conversation | Nowhere committed; `.aidlc/` (ignored) if it must persist locally | Everywhere |

Rules that follow: paths in artifacts are repository-relative; decisions are recorded as decisions ("the engineer chose X because Y"), never as transcript; a lesson goes to the knowledge store the repository already names in its `CLAUDE.md` or `docs/repo-profile.md` (for example `.claude/knowledge/`), and `<root>/solutions/` is created only where it already exists or the engineer adopts it. `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/aidlc.py" lint-artifacts [--root <repo>] [<change-id>]` flags the mechanical part (`session-uri`, `machine-path`) one `path:line` per hit and exits 1; `lbvs-aidlc-review` runs it before reading `review.md` back, and `lbvs-aidlc-conventions-checker` reports every hit as an Important `K<n>` finding, so `/lbvs-aidlc-ship` asks **Fix findings first** before such content is committed. The narrative part stays a review rule.

## A simple same-change handoff

Each stage hands the next one its saved file and nothing else. Intent reads the request and, when one exists, a ticket-seeded draft or a saved `spike.md`; design reads `intent.md` and the affected code; plan reads `intent.md`, `spec.md` and the code; build saves the confirmed proposal as `plan.md` and reads it back before implementing; verify reads `spec.md` and `plan.md` and writes the per-R-ID coverage table; review reads all of them with the real diff; ship reads `review.md` and the evidence from disk. Every stage first reads the [repository context](WORKFLOW.md#repository-context) that is present. The stage order, gate questions, flow policy, [review loop](WORKFLOW.md#review-loop-and-escalation) and ship options are in [stage gates and the flow policy](WORKFLOW.md#stage-gates-and-the-flow-policy) and [shipping a reviewed change](WORKFLOW.md#shipping-a-reviewed-change).

The handoff is the artifact content plus known conversation context, not a status string or a service event. A skill invocation grants no new permissions. Missing task inputs call for focused questions, not requests for unrelated CI, admin or service access.

### Pausing and resuming

A snapshot under `changes/<change-id>/handoffs/<topic>.md` holds actual progress (completed and unfinished work), decisions with their provenance (user-attributed versus inferred), evidence scope (observed and not-run checks), open questions, pending reviews, the relevant current files and one concrete next action. It is immutable and pointer-first; the canonical plan stays the live progress record. When to write one, what `lbvs-aidlc-resume` does with it and what a snapshot cannot carry (a worktree, uncommitted files, native scratch, credentials, approval) are in [durable handoff and resume](WORKFLOW.md#durable-handoff-and-resume).

### Ideas and reusable lessons

An ideation file holds ranked candidates and the rejected alternatives with reasons; a later intent reads the exact selected idea and links its provenance, and the ideation file stays supporting material rather than a second plan. A learning file holds one lesson with the fields in the table above and cites real verification. When to write either, and what CE lightweight capture may also touch, are in [compare directions before intent](WORKFLOW.md#compare-directions-before-intent) and [capture one non-obvious lesson](WORKFLOW.md#capture-one-non-obvious-lesson).

## Human decisions without approval machinery

Decision notes in an artifact are optional. When written, they record what was decided and why, preserving the meaning of the conversation, and never an invented approver, signature, timestamp, immutable commit or external review URL. `Status: draft` is a working label, not a state machine, a permission grant or an acceptance test. The rules are in [decisions without an approval service](WORKFLOW.md#decisions-without-an-approval-service).

## Sources and artifact synchronisation

Use source links, file locations, and code revisions or working-tree scope where they help another engineer understand the work. There is no mandatory provenance form, and a local request needs no external ticket. If a ticket, design tool or other system is authoritative, read the available records and link them; surface conflicting information for a human decision rather than choosing the convenient copy. Do not claim remote write-back or synchronisation unless an authorised update succeeded. Missing access is a specific limitation, not permission to invent source content or acquire more credentials.

When requirements or design change, update `spec.md` and revisit the affected plan tasks. When implementation departs from the plan, update `plan.md` alongside the code and explain why; keep them together in any eventual authorised commit. Revisit the intent if the outcome or scope changes. Preserve useful prior decisions without implying they cover materially different content.

### Optional CE discovery input

When the engineer chooses [CE brainstorming](WORKFLOW.md#optional-compound-engineering-discovery), its requirements document or returned chat brief is input to `intent.md`, which links the exact source path (CE writes under its configured artifact root, normally `docs/plans/`), carries the supported requirements, acceptance examples, scope, decisions and unresolved questions, and notes that the AIDLC files are the working records from then on. A chat brief needs no extra discovery file. What a blocked, missing or wrong-change CE result may and may not contribute is in that WORKFLOW section.

## Evidence and review

Planned proof belongs in the spec and plan; observed results belong in the implementation handoff or the review report. Verify's table has one row per R-ID with the check, the observed result, or `not run` with its reason ([traceability](WORKFLOW.md#traceability-from-requirement-to-check)); each executed check names the actual command or interaction, environment, checked code scope, result and evidence reference, and passed, failed and not-run checks stay apart. When the engineer accepts the verify stage's offer, `lbvs-aidlc-test-critic` adds `C<n>` findings with Important or nit severity and a "Not examined" list, which review reads as context; it alters no R-ID row and blocks no gate.

[Optional CE document review](WORKFLOW.md#optional-ce-document-review) critiques the exact saved spec or plan rather than a code diff; its findings default to conversation output, not automatic writes to `review.md`, spec or plan. [Verification](WORKFLOW.md#verification-is-still-part-of-the-work) stays ordinary task verification: software tests, bug reproductions and regression checks, runtime observations, and visual inspection for UI changes. Unavailable tooling or task dependencies leave specific behaviour unverified and are reported as such.

For a bug fix, `evidence.md` is the record. It states the EARS triad Current, Expected and Unchanged (`SHALL CONTINUE TO`), cites the reproduction, root cause, actual verification output and any Jira, PR or incident reference that really exists, and states under **Limits** when no regression test was kept. When the symptom arrived through an alert or incident link, the fix skill offers a `docs/incidents/` record and links it from References; a security defect also earns an offer of a `docs/security/findings/` record. The file feeds review, `lbvs-aidlc-learn` and `lbvs-aidlc-ship`, which reads it as a precondition and writes the PR URL back. It does not replace `review.md` when a review ran. The failing-test-first sequence, the fix marker and the reproduction commit are in the [bug-fix evidence loop](WORKFLOW.md#bug-fix-evidence-loop).

`review.md` records each pass with its tier, its findings with stable IDs and Important or nit severity, and each finding's disposition; any actual PR findings identify the inspected scope and follow-up evidence. The review skill passes the packet to an available reviewer at the tier in force and does not install or vendor a reviewer, implement an engine or invent provider commands ([review without rebuilding the reviewer](WORKFLOW.md#review-without-rebuilding-the-reviewer)). A local report needs no PR. A clean pass (zero open Important findings) is what `/lbvs-aidlc-ship` requires before it asks its question; it is not human approval, proof of deployment or a reason to bypass configured safeguards.

## Deferred work

The deferred work (evaluation runners, configuration-regression gates, approval enforcement, delivery execution, maintenance automation) is listed under [Later](WORKFLOW.md#later). The source, coverage and evidence documents are context for it, not a checklist an engineer completes before a local change; upstream source snapshots remain historical records, and local artifact work does not claim the deferred controls are installed, effective or verified.
