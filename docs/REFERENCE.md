# Reference

The complete description of what lbvs-aidlc contains and how each part behaves. Start with the [README](../README.md) and the [usage recipes](USAGE.md); come here when you need the exact contract, table or path.

## Helper

Python 3 is sufficient for the helper; no third-party Python packages are required. Claude Code and authorised model access are required for the skills.

```sh
python3 scripts/aidlc.py doctor
python3 scripts/aidlc.py doctor --install
python3 scripts/aidlc.py check
python3 scripts/aidlc.py mode
python3 scripts/aidlc.py conventions
python3 scripts/aidlc.py new example-change
python3 scripts/aidlc.py lint-artifacts --root ../my-service example-change
```

Replace `example-change` with the real change ID (`^[a-z0-9]+(-[a-z0-9]+)*$`). `new` creates only `changes/example-change/intent.md` as a draft and refuses to overwrite. `mode` prints one line, `AIDLC project mode: greenfield` or `brownfield`, with its reasons; `.aidlc/mode` containing either word overrides detection. `doctor` reports `python3`, `git` and `claude`, the optional tools the skills use when present (`graphify`, `codegraph`, `gh`, `omp`) and, for every server declared in `.mcp.json`, what authentication it needs and whether the environment variable is set; `doctor --install` additionally runs the listed installer (`uv tool install` or `pipx`, `npm install -g`, `brew install`) for each missing optional tool and nothing else — it never installs plugins, edits settings or connects a server. None of the commands approve, commit, push or deploy.

`lint-artifacts` scans `changes/<change-id>/**/*.md` (every change when the ID is omitted) and `docs/solutions/**/*.md` under `--root` (default: the repository around the current directory) for the mechanical half of the [content boundary](ARTIFACTS.md#content-boundary): `session-uri` (`artifact://`, `agent://`, `history://`, `local://`, `xd://`) and `machine-path` (`/Users/`, `/home/`, `/tmp/`, `/var/folders/`, `/private/`, drive letters). One `path:line: <rule> <text>` per hit, exit 1 on any, `lint-artifacts: clean (<n> files)` otherwise. `lbvs-aidlc-review` runs it before reading `review.md` back; `lbvs-aidlc-conventions-checker` reports each hit as an Important `K<n>` finding before ship.

`conventions` compares the repository with the defaults in `templates/conventions/` (`.editorconfig`, `.pre-commit-config.yaml`, `ruff.toml`, `biome.json`, `CONVENTIONS.md`) and reports, per file, whether the repository already owns that concern (an existing `pyproject.toml`, ESLint or Prettier config, `CONTRIBUTING.md` counts) or a default is available; `conventions --apply` copies only the missing defaults and never overwrites. Greenfield repositories are told to adopt; brownfield repositories are told to keep their own, which `lbvs-aidlc-onboard` records in the repository `CLAUDE.md`.

For a separate target directory, put the root option before the subcommand: `python3 scripts/aidlc.py --root /path/to/project new example-change`. This creates an intent there; it does **not** install the package into that repository.

## MCP servers

[.mcp.json](../.mcp.json) declares three remote (HTTP) servers and no credentials: **context7** (`https://mcp.context7.com/mcp`, current library docs; works anonymously with lower rate limits — set `CONTEXT7_API_KEY` to the literal value `Bearer <key>` for more), **github** (`https://api.githubcopilot.com/mcp/`; requires `GITHUB_PERSONAL_ACCESS_TOKEN`, which `gh auth token` prints for the logged-in account) and **atlassian** (`https://mcp.atlassian.com/v2/mcp`; OAuth 2.1 in the browser the first time you run `/mcp`). Claude Code asks once per project before connecting project-declared servers, and `python3 scripts/aidlc.py doctor` reports which variables are set. The ECC catalog under `mcp-configs/` is a verbatim upstream snapshot for reference only — its GitHub entry is outdated — so the live configuration is `.mcp.json`. `.claude/settings.local.json` is ignored and never exported; `.aidlc/fix/` and `.codegraph/` are ignored. Inherited user/managed settings, hooks and MCP connections still apply. The hooks are integrity and guardrail aids, not approval or security boundaries. See [runtime-file usage](USAGE.md#project-runtime-files-and-shared-instructions).

## Export and adoption

```sh
python3 scripts/aidlc.py package /path/to/new-aidlc-copy
python3 /path/to/new-aidlc-copy/scripts/aidlc.py check
```

The destination must not exist and its parent must exist. Export includes the declared skills, agents, templates, shared guidance, the helper, settings, hooks, rules, `.worktreeinclude`, `.mcp.json`, the `docs/adr/`, `docs/incidents/`, `docs/security/`, `docs/references/` and `docs/platform/` indexes and templates (plus any record they link), `templates/conventions/`, the vendor manifests and locally linked reference/evidence files. It does not copy Git history, `changes/` artifacts, solution/ideation stores, `.aidlc/`, local settings, credentials or plugin installations. Content is copied verbatim, **not secret-scanned**; inspect it before sharing.

Launch Claude in the exported tree to use it. For an **existing codebase**, use `python3 scripts/aidlc.py install <repo>` (report) then `install <repo> --apply`: it writes the AIDLC assets that are absent, keeps any existing file that differs, never creates or overwrites the eight repository-owned files (`AGENTS.md`, `CLAUDE.md`, `.gitignore`, `.claude/settings.json`, `.mcp.json`, `.worktreeinclude`, `.omp/AGENTS.md`, `.omp/config.yml`) — it prints a merge hint and the hooks block for each — and leaves the package's own docs and integrity hook behind. `.aidlc/manifest.json` records the package revision and a hash per installed file; a knowledge store the repository already keeps (`docs/adr/` with content, say) is not seeded with our index and template and stays skipped. `sync <repo> [--apply]` later compares package, manifest and repository three ways and updates only files you have not edited, reporting conflicts, upstream removals and local edits without touching them; `update [--from <pkg>] [--apply]`, run inside the adopting repository, clones the source recorded in the manifest and runs that clone's `sync`. None of them commits; `--add-dir` alone is not a supported installation. See the [adoption recipe](USAGE.md#11-install-into-an-existing-repository-or-export-a-new-one).

## Commands

Every command accepts exactly one ID matching `^[a-z0-9]+(-[a-z0-9]+)*$`: a change ID, except `lbvs-aidlc-ideate`, which takes a topic ID, `lbvs-aidlc-ticket`, which takes a ticket key or issue URL, and `lbvs-aidlc-init` and `lbvs-aidlc-onboard`, which take none. Put context, paths, CE selection and requested actions in conversation, not extra arguments.

| Command | Purpose |
| --- | --- |
| `/lbvs-aidlc <change-id>` | Start or continue a change: propose a worktree, read the project mode (brownfield without a conventions record runs `lbvs-aidlc-onboard` first), ask the kind of work — *Feature/change*, *Bug fix* (→ `lbvs-aidlc-fix`) or *Spike/investigation* (→ `lbvs-aidlc-spike`) — then run intent → design → plan → build → verify → review with a stage gate after each, drive the review loop (fix → verify → re-review, at most three fix cycles) and hand a clean pass to `lbvs-aidlc-ship` when you choose. Given a ticket key instead of a change ID, it points you at `/lbvs-aidlc-ticket`. |
| `/lbvs-aidlc-ticket <KEY or issue URL>` | Ticket intake: read the Jira issue (Atlassian MCP) or GitHub issue (`gh issue view` or the github MCP) read-only, derive and confirm `<key>-<slug>`, write `.aidlc/current`, create `intent.md` from the ticket's summary, description, acceptance criteria and link, then offer to continue with `/lbvs-aidlc`. Never writes back to Jira or GitHub; asks you to paste the ticket when no connector is available. |
| `/lbvs-aidlc-spike [change-id]` | Time-boxed read-only investigation: agree the question, the time box and what "answered" means, investigate (Explore, `lbvs-aidlc-repo-scout`, graphify when present, docs), save `changes/<change-id>/spike.md` with sourced findings, options, a recommendation and open questions, then offer to create/refresh the intent or record an ADR. Never implements. |
| `/lbvs-aidlc-intent <change-id>` | Clarify problem, outcome, scope and questions into `intent.md`. |
| `/lbvs-aidlc-design <change-id>` | Turn intent and repository context into `spec.md`: acceptance criteria as EARS lines with stable IDs (`R1.1`), library APIs resolved through Context7 first, `docs/platform/platform.md` read when present (a new store, queue or integration needs a platform entry and a threat-model offer). Before the design gate, the read-only `lbvs-aidlc-design-reviewer` agent returns READY / NOT READY with numbered findings as a summary input — never an approval. |
| `/lbvs-aidlc-plan <change-id>` | Propose an implementation plan read-only; numbered checkbox tasks `- [ ] T1.2 …` each ending `_Requirements: R1.1, R2.3_` (plus `depends on:` where relevant), and the skill checks every R-ID appears in at least one task. Deployment or observability changes are expressed as values/pipeline config for the delivery orb. Standalone planning supported. |
| `/lbvs-aidlc-build <change-id>` | Save the confirmed plan (save-only on request), then implement one task at a time in order (or the task you name): run that task's own check, tick `[x]` in `plan.md` only after it passes, never tick ahead; run the repository's pre-commit/lint before declaring a task done (greenfield without any: mention `conventions --apply`). |
| `/lbvs-aidlc-verify <change-id>` | Exercise changed behaviour; report a table `R-ID \| check \| observed result \| not run (reason)` — coverage by requirement, not just by command — without fixing code. |
| `/lbvs-aidlc-review <change-id>` | Hand artifacts and evidence to an existing reviewer at a tier (standard `/code-review high` by default; escalated `xhigh` after a fix pass; `max` and cloud `ultra` on request); findings are **Important** or **nit** with stable IDs (`R1`, `R2` …) that persist across passes; each pass is recorded in `review.md`. |
| `/lbvs-aidlc-fix <change-id>` | Bug-fix loop: reproduce, commit a failing test, protect it, fix, verify, write `changes/<change-id>/evidence.md` — with the EARS triad Current / Expected / Unchanged (*SHALL CONTINUE TO*) that the reproduction and regression tests map to — and Jira/PR references, offer a lesson. |
| `/lbvs-aidlc-ship [change-id]` | Ship a reviewed change: reads `review.md` (latest pass must have zero open Important findings) and the verify evidence from disk, shows `git status`/diff and the commits ahead of the default branch (only the [reproduction commit](WORKFLOW.md#reproduction-commit) is expected; anything else needs confirmation), requires branch `aidlc/<id>` (refuses the default branch), delegates to `lbvs-aidlc-conventions-checker` — documented commands, conventions, hygiene, glossary and `lint-artifacts` — and shows its `K<n>` findings and commands table, then asks exactly *Commit, push and open PR* / *Commit only* / *Stop here* — or, with any Important finding, *Fix findings first (lbvs-aidlc-build)* / *Ship anyway: commit, push and open PR* / *Stop here*, listing accepted K-findings in the PR body. Commit title `VS-1234: <imperative>` when the ID starts with a Jira key, else a Conventional Commit type; body: why + `Change: <id>`; `changes/<id>/` artifacts committed with the code. Push to `origin` only after the explicit choice, never force, never to the default branch; PR via `gh pr create --base <default branch>` (github MCP when `gh` is absent) with the bundled `templates/pr-body.md`; the PR URL is read back into `review.md`/`evidence.md` and committed as `docs(<id>): record PR #<n>` under the same choice, so the tree ends clean. Never merges, approves, enables auto-merge or edits branch protection. |
| `/lbvs-aidlc-init` | Repository setup wizard, idempotent and report-first: `doctor` (offer `--install`), project mode (brownfield hands over to `lbvs-aidlc-onboard`; greenfield asks *Adopt default conventions (`python3 scripts/aidlc.py conventions --apply`)* / *Keep my own tooling* / *Decide later* and names the app-template route), fill discoverable items of `docs/platform/platform.md` read-only from `.circleci/config.yml`, `deploy/`, `catalog-info.yaml` and `Taskfile.yml`, state what MCP/CE still needs auth or install without doing it, offer `/graphify .` when graphify is present, report whether the optional `lbvs-aidlc-observer@lbvs-aidlc` observer plugin is enabled (from the session catalogue) and on request print its enable command — running and writing nothing, propose at most three repository-specific agents or skills with the reason an existing agent does not cover each (drafted from `templates/agent.md`, written only on confirmation), offer missing `.gitignore` lines, then summarise and ask exactly *Start a change (/lbvs-aidlc)* / *Start from a ticket (/lbvs-aidlc-ticket)* / *Done*. Mentions `/init` with `CLAUDE_CODE_NEW_INIT=1` and the official `skill-creator`/`plugin-dev` plugins as alternatives. |
| `/lbvs-aidlc-onboard` | Brownfield onboarding: `lbvs-aidlc-repo-scout` conventions report, `python3 scripts/aidlc.py conventions` (report only, existing tooling recorded in the `CLAUDE.md` draft, never overwritten), modernize/legacy decision (*Modernize (adopt current patterns)* / *Stay legacy (inherit existing style)* / *Decide later*), proposed repository `CLAUDE.md`, `.claude/rules/` and `docs/repo-profile.md` drafts written only on confirmation (options *Write CLAUDE.md, rules and repo profile* / *Write repo profile only* / *Do not write*); an existing fresh profile skips the scout, a stale one re-derives only the sections whose manifests changed. Greenfield: asks *Adopt default conventions (`python3 scripts/aidlc.py conventions --apply`)* / *Keep my own tooling* / *Decide later* and, when the project needs cloud delivery, points at `docs/platform/README.md` (app-template route). |
| `/lbvs-aidlc-learn <change-id>` | Capture one verified, non-obvious lesson with `Confidence`, `Observations` and `Scope`, or honestly skip; written to the knowledge store the repository already names in `CLAUDE.md` or `docs/repo-profile.md`, else `<root>/solutions/` where that exists or is adopted; when a same-topic lesson is re-observed, offer to bump its Observations/Confidence instead of writing a duplicate. Returns to the gate that offered it. |

| Manual utility | Purpose |
| --- | --- |
| `/lbvs-aidlc-handoff <change-id>` | Immutable snapshot under `changes/<change-id>/handoffs/`. |
| `/lbvs-aidlc-resume <change-id>` | Read-only orientation from a selected snapshot or current artifacts, then stop. |
| `/lbvs-aidlc-ideate <topic-id>` | Compare and save candidate directions before a change is chosen. |

**Stage gates.** At the end of each stage the skill summarises the artifact path, decisions, open questions and checks run, then asks: *Proceed to \<next stage\>*, *Revise this stage*, or *Stop here*. Only *Proceed* (or an announced auto-advance under a stated policy) invokes the next skill. After review the options are exactly *Fix findings (build)*, *Re-review at higher effort*, *Open PR (lbvs-aidlc-ship)*, *Capture lesson (lbvs-aidlc-learn)*, or *Done*.

**Review loop.** Tiers map to the bundled `/code-review` effort argument: **standard** = `high` (default first pass), **escalated** = `xhigh` (every re-review after a fix pass), **maximum** = `max`, **cloud** = `ultra` (multi-agent cloud review; costs more and needs the cloud feature) — the last two only when you pick *Re-review at higher effort* or say so. Severity follows [REVIEW.md](../REVIEW.md): **Important** versus **nit**. The loop is review → Important findings → fix (`lbvs-aidlc-build` with the agreed finding IDs) → verify → re-review at escalated … until a pass returns zero Important findings or **three fix cycles** have run, after which it always stops and asks. Under `Flow policy: auto-advance when clear, including build` those fix → verify → re-review cycles may continue by themselves up to the cap, announcing each hop; the review pass itself always presents its findings and the post-review gate is always asked. Finding IDs (`R1`, `R2` …) are stable across passes, and `review.md` records each pass with its tier, findings and disposition.

**Knowledge offers.** `lbvs-aidlc-design` offers an ADR when the spec introduces or changes an architectural boundary, technology choice or contract, and a threat model when it introduces a new external interface, data store, credential or trust boundary; `lbvs-aidlc-review` reports an architectural change without an ADR as a finding (not a blocker); `lbvs-aidlc-fix` offers an incident record when the symptom arrived through an alert or incident link, and a security finding record for security defects. Every offer is an AskUserQuestion; nothing is written automatically.

**Worktrees.** `/lbvs-aidlc` and `/lbvs-aidlc-fix` start by proposing a dedicated branch/worktree named `aidlc/<change-id>` (EnterWorktree when available, otherwise `git worktree add ../<repo>-<change-id> -b aidlc/<change-id>`) and ask before creating it.

Planning does not save `plan.md`; `lbvs-aidlc-build` saves the exact confirmed proposal after the normal writable transition. The skills are advisory instructions, not security controls; existing repository rules and tool permissions apply. Six subagents live under `.claude/agents/`: `lbvs-aidlc-verifier` (Bash-capable fresh check), `lbvs-aidlc-conventions-checker` (Read, Glob, Grep and Bash bounded to the commands `docs/repo-profile.md` or `CLAUDE.md` documents — run verbatim, never `--fix`; then the diff against naming, layout, generated paths, out-of-plan files and credential-looking strings; commit-title format and `changes/<id>/` presence; an ADR when a boundary changed; glossary drift as a nit — findings `K1…` with a commands table, run by `lbvs-aidlc-ship` before its question; adapted from the AWS quality and developer agents, MIT-0, and ECC's code-reviewer, MIT), and four read-only ones (Read, Glob, Grep) — `lbvs-aidlc-repo-scout` (conventions report for onboarding and spikes), `lbvs-aidlc-design-reviewer` (adversarial pass over `spec.md`/`plan.md` against intent, ADRs, `platform.md` and conventions — requirements coverage and EARS quality, consistency with ADRs, platform fit, NFR gaps, missing threat model — verdict READY / NOT READY with numbered findings, invoked by `lbvs-aidlc-design` before its gate; adapted from awslabs/aidlc-workflows, MIT-0) and `lbvs-aidlc-threat-modeler` (a STRIDE table for a named boundary from `docs/security/threat-model-template.md` with a false-positive list — test fixtures, accepted risks documented in `docs/security/`, framework-handled CSRF/escaping when verified — invoked when a threat-model offer is accepted; adapted from the AWS devsecops agent, MIT-0, and ECC's security-reviewer false-positive list, MIT) and `lbvs-aidlc-test-critic` (a change's tests against the spec's R-IDs: a coverage table, implementation-coupled or tautological tests, failure/boundary/concurrency cases named in EARS IF/WHILE lines but untested, flaky patterns, and for a fix whether the reproduction test exists and stayed protected — findings `C1…` as **Important** or **nit** with the smallest fix; offered by `lbvs-aidlc-verify` after its R-ID table and listed in the review packet; idea adapted from ECC's pr-test-analyzer, MIT). Each has an `.omp/agents/` counterpart. `/lbvs-aidlc-init` may add repository-specific agents from its bundled `templates/agent.md`. No commit, push, PR, merge or deployment happens without your explicit authorisation.

| `docs/repo-profile.md` (in the adopting repository; template at [`repo-profile.md`](../.claude/skills/lbvs-aidlc-onboard/templates/repo-profile.md)) | Header `Last verified: <date> at <commit>` and `Manifests: <paths>`, then Identity (company, glossary file, platform), Stack, Layout, Commands verbatim, Conventions, Testing, Generated paths, Hotspots, Ownership, Existing agent instructions, Playbooks, Open questions. `python3 scripts/aidlc.py profile` prints `missing`, `fresh` or `stale (<n> manifest commits since <rev>)` | `/lbvs-aidlc-onboard` and `/lbvs-aidlc-init` from the `lbvs-aidlc-repo-scout` report, on confirmation; every stage reads it before scouting |
| [`docs/glossary/`](glossary/README.md) | [`logicbroker-glossary.md`](glossary/logicbroker-glossary.md) (58 terms) and [`virtualstock-glossary.md`](glossary/virtualstock-glossary.md) (51 terms): term, aliases and code names, topic, evidence label, definition, usage, review question, sources pinned to a commit; each links its Confluence review copy; [`logicbroker-glossary-comparison.md`](glossary/logicbroker-glossary-comparison.md) is the reconciliation guide against the product team's glossary; [`template.md`](glossary/template.md) is the blank entry | Domain owners on Confluence, copied back in a reviewed PR; `lbvs-aidlc-intent`/`lbvs-aidlc-design` use terms verbatim and offer an entry for a **new term**; `lbvs-aidlc-review` and the checker report drift as a nit |
| [`docs/playbooks/`](playbooks/README.md) | `<kebab-title>.md` from [`template.md`](playbooks/template.md): Status, `Last verified`, `Runs: <count> (<change IDs>)`, Trigger, Preconditions, numbered Steps each with its check, Verification, Rollback, Pitfalls, Sources, Promotion (Verified and Runs ≥ 3 → proposed as a repository skill by `/lbvs-aidlc-init`, never auto-written) | `lbvs-aidlc-spike` (*Save as playbook*), `lbvs-aidlc-learn` (*Save as playbook instead*); `lbvs-aidlc-plan` cites a matching one per task, `lbvs-aidlc-build` follows it and offers the Runs bump |

The test for where something belongs: **a recurring correction becomes a rule** in `AGENTS.md` or `.claude/rules/`, not a record; a record holds a decision, an event or a lesson with its evidence and freshness. A lesson observed in **≥2 changes with confidence ≥0.8** is a *candidate* rule for `AGENTS.md`/`.claude/rules/` — proposed to the engineer, never auto-written. The confidence ladder and promotion rule borrow the record schema from ECC's `continuous-learning-v2`. That skill is vendored complete at the pin (`.claude/skills/continuous-learning-v2/`: Pre/PostToolUse `observe.sh`, background `claude --model haiku` observer scripts, instinct CLI) but **off by default**: nothing in this package registers its hooks, and `/lbvs-aidlc-init` only reports whether the separate `lbvs-aidlc-observer@lbvs-aidlc` plugin (`defaultEnabled: false`) is enabled and prints the enable command. When an engineer enables it, observations (tool inputs and outputs) and personal instincts are stored under `${XDG_DATA_HOME:-~/.local/share}/ecc-homunculus/`, never in the repository, and the model calls run on that engineer's account. It is distinct from `/lbvs-aidlc-learn`, which stays the confirmed, per-change lesson in `docs/solutions/`; an instinct becomes shared knowledge only when an engineer promotes it through review. Skills read these files at equal weight, so mark a lesson *Needs re-check* or supersede an ADR rather than letting stale text mislead. The model is adapted from the team-knowledge chapter of AWS's [aidlc-workflows](https://github.com/awslabs/aidlc-workflows/blob/main/docs/harness-engineering/07-team-knowledge.md) and the ADR template shape used by the sibling Logicbroker `shared-services-aidlc` repository; the text here is our own. Hosted scans, incident channels and monitoring that would feed these stores automatically remain [deferred](../FUTURE_WORK.md#f5--maintenance-and-operational-feedback).

## Review and delivery boundaries

Prefer an existing reviewer over a custom engine. [Review options](../.claude/skills/lbvs-aidlc-review/references/review-options.md) supplies scope capture, a complete context packet and provider handoffs; the review loop above bounds escalation and fix cycles. If invocation is unavailable the result is **prepared — not run**, never fabricated findings. Fixes, remote comments, commits, merges and deployment require separate authority: `/lbvs-aidlc-ship` is the one skill that commits, pushes and opens a PR, and it does so only after you pick that option — it never merges, approves, enables auto-merge or edits branch protection. Running pipelines and promoting images stay with CircleCI and a human ([deferred](../FUTURE_WORK.md#f4--delivery-integration-through-circleci)); `docs/platform/` only tells the stages what exists.

## Design decisions


- **Names carry the package prefix.** Commands are `/lbvs-aidlc` and `/lbvs-aidlc-<stage>`, agents `lbvs-aidlc-<role>`, so they stay distinct from the other AIDLC packages an engineer may have loaded (AWS `aidlc-workflows`, `shared-services-aidlc`, `product-aidlc`) and from the plugin form `/lbvs-aidlc:lbvs-aidlc-<stage>`. Unchanged: the branch prefix `aidlc/<change-id>`, the `.aidlc/` state directory, `changes/`, the helper `scripts/aidlc.py`, the `AIDLC project mode:` line and "AIDLC" as the name of the lifecycle. Renamed 2026-09-17; `docs/VERIFICATION.md` keeps the earlier names in its history.
- **Instructions.** `AGENTS.md` is the one shared instruction file (under 60 lines, ends with *Things Claude gets wrong here*). `CLAUDE.md` is `@AGENTS.md` plus a Claude-only section and `.omp/AGENTS.md` is `@../AGENTS.md` for Oh My Pi; `check` rejects duplicated text or symlinks. Codex reads `AGENTS.md` directly.
- **Stages are model-invocable.** `/lbvs-aidlc` orchestrates; each stage ends at an explicit confirmation gate. Only `lbvs-aidlc-handoff`, `lbvs-aidlc-resume` and `lbvs-aidlc-ideate` are manual.
- **Hooks stay narrow and deterministic.** Two `SessionStart` context hooks (package check, project mode), one `PreToolUse` guardrail that exists only while a bug fix is in progress, and one `WorktreeCreate` hook that only names the worktree. No approval gates or formatters — those belong to the adopting repository.
- **Bugs leave evidence.** `/lbvs-aidlc-fix` writes the failing test first and, on the engineer's *Commit now*, makes the one [reproduction commit](WORKFLOW.md#reproduction-commit) allowed before ship; it protects the test in the repository that owns it, probes the hook before implementing, records `changes/<id>/evidence.md` with Jira/PR/incident references and the executed source identity, offers `/lbvs-aidlc-learn` and re-asks its gate afterwards.
- **Brownfield is detected, not assumed.** `mode` classifies the repository at session start (≥10 code files or ≥20 commits; `.aidlc/mode` overrides); `/lbvs-aidlc-onboard` scouts read-only and asks modernize vs stay-legacy before drafting a repository `CLAUDE.md`.
- **Every change runs in a worktree** on branch `aidlc/<change-id>`; `.worktreeinclude` carries `.env` and local settings into it.
- **Non-technical entry** is optional Compound Engineering brainstorming; **caveman** is per-engineer opt-in; **ECC skills** are vendored and untouched by AIDLC work.
- **Requirements are traceable.** Acceptance criteria in `spec.md` are EARS lines with stable IDs (`R1.1`: *WHEN … THE <system> SHALL …*); every `plan.md` task ends `_Requirements: R1.1, R2.3_`; build works one task at a time and ticks it only after its check passes; verify reports coverage per R-ID. Ideas from [Kiro specs](https://kiro.dev/docs/specs/), adopted without Kiro's tooling.
- **Review is a bounded loop.** `/code-review` effort maps to tiers (standard `high`, escalated `xhigh`, maximum `max`, cloud `ultra`); findings are **Important** or **nit** with stable IDs; review → fix → verify → re-review runs at most three fix cycles before it always stops and asks.
- **Shipping is a skill that always asks.** `/lbvs-aidlc-ship` reads the review and evidence from disk, runs the conventions checker, offers exactly *Commit, push and open PR* / *Commit only* / *Stop here*, titles commits with the Jira key (`VS-1234: …`) and never merges, approves or touches branch protection. It stays **model-invocable** so the review and fix gates can hand off to it directly — a deliberate deviation from Claude Code's guidance to mark commit/deploy skills `disable-model-invocation: true` (decided 2026-09-17); the skill's own question is the barrier before any git command, and no flow policy reaches it without the engineer answering the review gate. Flip the frontmatter and `MANUAL_SKILLS` in `scripts/aidlc.py` together if that trade-off changes.
- **Current docs, not training data.** Design, plan, build and fix resolve library APIs through the `context7` MCP first and log what settled a real question in `docs/references/libraries.md`.
- **Platform is pointed at, not duplicated.** `docs/platform/` names `Logicbroker/app-template` and the `lb-pipelines/app-delivery-kit-vs@1` orb; each adopting service records its own facts in `platform.md`. Delivery execution stays deferred.
- **Conventions default, never overwrite.** `templates/conventions/` plus `python3 scripts/aidlc.py conventions [--apply]`: greenfield adopts the defaults on request, brownfield keeps its own.
- **Lessons carry confidence.** Each lesson records `Confidence`, `Observations` and `Scope`; a lesson observed in ≥2 changes at confidence ≥0.8 is *proposed* as a rule, never auto-written. The schema is borrowed from ECC `continuous-learning-v2`, vendored complete but off by default: its hooks run only through the separate `lbvs-aidlc-observer@lbvs-aidlc` plugin an engineer enables, storing observations outside the repository.

## Working without ceremony


- **No IDs to remember.** `/lbvs-aidlc` with no argument resolves the change from the branch (`aidlc/<id>`), then `.aidlc/current`, then the only change without `review.md`, and asks only if none of those answer. `python3 scripts/aidlc.py status` lists every change with the stage artifacts present, the stage reached and the next one; `current` prints just the ID and its source.
- **Descriptive branches with your ticket key.** Change IDs are `^[a-z0-9]+(-[a-z0-9]+)*$`, so prefix the ticket: `vs-1234-order-export`. The `WorktreeCreate` hook then produces `.claude/worktrees/aidlc+vs-1234-order-export` on branch **`aidlc/vs-1234-order-export`** (branched from local `HEAD`) instead of Claude Code's default `worktree-…` name, and copies `.worktreeinclude` files itself. Non-AIDLC worktree names keep the default shape. Because the hook replaces the host's creation logic, Claude Code's worktree sweep leaves these alone: remove one with `git worktree remove`.
- **Gates or auto-advance, your choice.** `/lbvs-aidlc` asks the flow policy once per run: *confirm each stage*, *auto-advance when clear, stop before build*, or *auto-advance when clear, including build*. Auto-advance requires the stage to have saved **and read back** its artifact with no open questions, no failed or missing required check and no pending CE review; it announces each hop. The review pass always presents its findings and asks the post-review gate; only under *including build* may the fix → verify → re-review cycles continue by themselves, up to the three-cycle cap. Every commit, push, PR or deployment asks.

## Distribution


One branch, `main`, carries all three forms:

| Form | Where it lives | Use |
| --- | --- | --- |
| In-repo install | `python3 scripts/aidlc.py install <repo> [--apply]` / `sync <repo> [--apply]` / `update` (from the adopter) | Primary for existing services: the assets are committed in the adopting repository, so every host that reads `.claude/skills/` and `.omp/` has them on checkout. |
| Standalone export | `python3 scripts/aidlc.py package <new-dir>` | New services. |
| Claude Code plugin | `.claude-plugin/marketplace.json` + the generated `plugins/lbvs-aidlc/` tree, both committed on `main` | Teams that want namespaced, versioned skills (`/lbvs-aidlc:lbvs-aidlc <id>`) with nothing in the repository, per repository via `extraKnownMarketplaces` + `enabledPlugins` or fleet-wide via managed settings. Claude Code only: it has no `.omp/`. |

```sh
# plugin route
claude plugin marketplace add mkhan-lb/lbvs-aidlc
claude plugin install lbvs-aidlc@lbvs-aidlc
```

The plugin carries the AIDLC skills, all six agents, the helper (`scripts/aidlc.py`), the project-mode and test-protection hooks and the shared workflow docs (reached via `${CLAUDE_PLUGIN_ROOT}`); it does not carry the ECC library, a `CLAUDE.md`, the package-integrity hook, the worktree hook or `.omp/` — so under Oh My Pi a plugin-only repository has the skills but not the agents or the protect hook; use `install` there. Regenerate it with `python3 scripts/build_plugin.py` after changing any AIDLC skill, agent, hook or shared doc, in the same commit; `python3 scripts/aidlc.py check` runs `build_plugin.py --check` and fails on any drift between the sources and the committed `plugins/` tree, so the SessionStart hook reports a forgotten regeneration.
