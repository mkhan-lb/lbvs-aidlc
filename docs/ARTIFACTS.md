# Artifacts and engineer handoffs

Status: draft

The current contract is [WORKFLOW.md](WORKFLOW.md): **intent → design → plan → build → verify → review → fixes and re-review → ship**, run by `/aidlc [change-id]` with a gate after each stage — answered by the engineer, or auto-advanced only under a stated flow policy when nothing is open — plus the `/aidlc-fix` evidence loop and the `/aidlc-ship` commit/push/PR step that always asks. Requirements carry stable IDs from spec to plan to verification. This package adapts the artifact-oriented approach in [Anthropic's AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) to that workflow, with the traceability shapes borrowed from [Kiro specs](https://kiro.dev/docs/specs/). It does not implement the playbook's whole lifecycle.

A change ID uses lowercase ASCII letters or digits separated by single hyphens: `[a-z0-9]+(?:-[a-z0-9]+)*`. A ticket key fits as a lowercase prefix, so `vs-1234-order-export` is a valid ID that carries its Jira key. Use one stable ID for the whole change. Keep its canonical AIDLC artifacts in `changes/<change-id>/`; use different directories for different changes. You do not have to repeat the ID at every command: `python3 scripts/aidlc.py current` resolves it from the branch (`aidlc/<id>`, `aidlc+<id>`, `worktree-aidlc/<id>`, `worktree-aidlc+<id>`), then `.aidlc/current`, then the only change without `review.md`, and `python3 scripts/aidlc.py status` lists what exists. An unresolved ID is a question for the engineer, never a new `changes/<id>/` directory. External ticket IDs and optional discovery documents are source references, not permission tokens.

For ideas and lessons, `<root>` means the supporting artifact root: `docs` unless a valid repository `.compound-engineering/config.yaml` sets `docs_root`. The local override does not supply that key. Resolve it safely inside the repository, not at its root or under `.git/`; never create config or a second store. Learning stays associated with its source change; ideation has a separate topic ID and does not create canonical change artifacts.

Following the [official directory guide](https://code.claude.com/docs/en/claude-directory), active templates live beside the skill that owns them and are read on demand. Shared human-facing docs stay under `docs/`; `scripts/aidlc.py` stays a shared helper. These project-scoped bundles depend on that shared content, so copying one skill is not a standalone installation. Authored `changes/<change-id>/` files are durable working artifacts, not `.claude` runtime memory or native configuration. The knowledge-store templates (`docs/adr/template.md`, `docs/incidents/template.md`, `docs/security/threat-model-template.md`) live beside their indexes rather than in a skill bundle because more than one skill writes to them. Every knowledge record is written only after an explicit confirmation and read back afterwards; a recurring correction becomes a rule in `AGENTS.md` or `.claude/rules/`, not another record (see [knowledge stores](WORKFLOW.md#knowledge-stores)).

`python3 scripts/aidlc.py new <change-id>` creates a non-overwriting draft intent, substituting only literal `{{change_id}}`. Create later artifacts through their owning skills as work progresses; do not prefill them as completed work. The ideation template's `{{topic_id}}` is filled by that utility, not a generic helper templating engine. Replace instructional text with actual context, retaining meaningful unresolved questions rather than inventing facts.

The helper's subcommands are `check`, `doctor` (with `--install`), `mode`, `status`, `current`, `conventions` (with `--apply`), `profile`, `worktree`, `package` and `new`. None of them authorises implementation or verifies human approval: `status` and `current` only report which change artifacts exist, `doctor` only reports tool presence and MCP authentication needs (and, with `--install`, runs package-manager installers for missing optional tools), `conventions` only reports which default convention files the repository already owns (and, with `--apply`, copies the missing ones without overwriting), `profile` only reports whether `docs/repo-profile.md` is missing, fresh or stale against its recorded manifests and commit, and `worktree` only names and creates a worktree for the `WorktreeCreate` hook. See the [helper reference](REFERENCE.md#helper) for their interface; design decisions, project configuration, hosts, MCP servers and the knowledge-store tables are in [REFERENCE.md](REFERENCE.md). No external approval service, evaluation runner, or CI setup is required to use these artifacts.

`package <new-directory>` exports the declared package and locally linked resources as a complete standalone tree. It refuses an existing destination, unsafe/missing resources and working artifact stores. It does not install into another codebase or merge/replace its instructions. See the [adoption recipe](USAGE.md#11-export-and-adopt-without-overwriting-a-repository).

## A simple same-change handoff

1. **Worktree and mode:** `/aidlc` resolves the change ID (argument, branch, `.aidlc/current`, or the only open change), states the run's flow policy, proposes the `aidlc/<change-id>` worktree — created by the `WorktreeCreate` hook as `.claude/worktrees/aidlc+<change-id>` — and asks; it reads the project mode and, for brownfield without a conventions record, runs onboarding first; then it asks whether this is a feature/change, a bug fix (`aidlc-fix`) or a spike (`aidlc-spike`). Work that begins from a ticket key goes through `/aidlc-ticket` first, which fetches the record read-only, confirms the derived ID and seeds the intent.
2. **Intent:** read the request and relevant source material — a ticket-seeded draft or a saved `spike.md` when one exists — draft the problem/outcome/scope, and invite corrections from the engineer or requester. A conversation is enough to begin; no product-owner identity check or external review URL is required. Non-technical originators may arrive through CE brainstorming.
3. **Spec:** read that intent and affected code, define requirements as EARS criteria with stable R-IDs and the design, resolving any library API through Context7 first and reading `docs/platform/platform.md` when it exists; discuss unresolved trade-offs. Carry unanswered questions forward rather than silently deciding them. Before the gate, `aidlc-design-reviewer` reads the spec adversarially and returns READY / NOT READY with numbered findings — summarised as input, not approval. If selected, CE document review critiques the saved spec and returns findings without changing it. When the design introduces or changes an architectural boundary, technology choice or contract, the skill offers an ADR; when it introduces a new external interface, data store, credential or trust boundary, it offers a threat model (accepted, `aidlc-threat-modeler` drafts the STRIDE table for confirmation). Both are questions, never automatic writes.
4. **Plan:** read the same intent/spec and actual code in read-only plan mode. Propose numbered tasks with `_Requirements: R…_` trace lines and dependencies, sequence, risks, and proof; check every R-ID is covered. Do not save canonical artifacts or run tests/runtime commands while still in that mode. A native host-managed plan file is scratch state, not the saved AIDLC plan.
5. **Build:** after ordinary engineer confirmation and the normal authorised writable transition, `aidlc-build` saves the exact selected proposal to the canonical plan and rereads it. An explicit save-only request stops there without application changes or execution. If CE document review was requested, save first and return the exact saved plan for review before implementing. Implement one task at a time when requested: run that task's check, tick it in `plan.md` only after the check passed, run the repository's pre-commit/lint before calling the task done, and keep spec, plan, code and evidence aligned.
6. **Verify and review:** verify reports coverage per R-ID (`R-ID | check | observed result | not run (reason)`); once that map exists it asks **Critique the tests (aidlc-test-critic)** / **Skip** — accepted, the read-only critic returns `C<n>` findings (coverage gaps, implementation-coupled or flaky tests, missing failure cases) that the summary and the review packet carry as input, never as failures. Supply the artifacts, real diff, and observed checks to an available reviewer at the standard tier. Use [review options](../.claude/skills/aidlc-review/references/review-options.md) for provider-specific usage. Default to a local findings report with stable finding IDs and Important/nit severity; publish only on explicit request with authorised access.
7. **Fix and re-review:** address agreed Important findings by ID in an authorised implementation pass, rerun affected checks, and re-review at the escalated tier. Repeat until a pass returns zero Important findings or three fix cycles have run, then stop and ask. Record findings still open or dismissed with reasons in `review.md`. Human review and existing repository safeguards remain.
8. **Ship:** when the engineer chooses **Open PR (aidlc-ship)**, the skill reads `review.md` and the evidence from disk, shows the diff, delegates the pre-PR conventions check to `aidlc-conventions-checker` (documented commands rerun verbatim, diff against `docs/repo-profile.md`, delivery hygiene, glossary drift — `K<n>` findings shown in the summary, input not blockers), then asks **Commit, push and open PR** / **Commit only** / **Stop here** — or, with an Important K-finding, **Fix findings first (aidlc-build)** / **Ship anyway: commit, push and open PR** / **Stop here** — commits code and artifacts together (Jira-key title when the ID carries one), pushes `aidlc/<change-id>` and opens the PR from the body template, listing accepted K-findings in its Review section; the PR URL is read back into the artifacts. It never merges. Pipeline runs and promotion belong to CircleCI and a human.

Every stage first reads the [repository context](WORKFLOW.md#repository-context) that is present — `docs/repo-profile.md` (after `python3 scripts/aidlc.py profile` says it is fresh), the glossary the profile names, `docs/playbooks/README.md`, `platform.md`, `libraries.md` — and scouts only what is missing or stale.

Each stage ends with a summary (artifact path, decisions, open questions, checks run and their results). Under the default `Flow policy: confirm each stage` the skill then asks the gate question (**Proceed to \<next stage\>**, **Revise this stage**, **Stop here**) and the answer, not the summary, moves the work on. Under an auto-advance policy a stage may continue by itself only when its artifact was saved and read back, nothing is open, no check failed or was skipped, no requested review is pending, and the next step is neither build (unless the policy includes build) nor a commit, push, PR, merge, publication or deployment; it announces the advance in one line. The review pass always presents its findings and asks the post-review gate — exactly **Fix findings (build)**, **Re-review at higher effort**, **Open PR (aidlc-ship)**, **Capture lesson (aidlc-learn)**, **Done**; only under the policy that includes build may the fix → verify → re-review cycles continue by themselves, up to the three-cycle cap. No gate is ever answered on the engineer's behalf. See [stage gates and the flow policy](WORKFLOW.md#stage-gates-and-the-flow-policy) and the [review loop](WORKFLOW.md#review-loop-and-escalation).

The handoff is the actual artifact content and known conversation context, not a status string or a service event. A skill invocation does not grant new permissions. Missing task inputs call for focused questions, not requests for unrelated CI/admin/service access.

### Pausing and resuming

`aidlc-handoff` creates a requested snapshot under the same change's `handoffs/` directory, through ordinary writable permissions. Keep snapshots immutable and pointer-first; capture actual progress, decisions with provenance, evidence scope, open questions, pending reviews and a concrete next action. The canonical plan remains the live implementation/progress record. Do not create a snapshot or save a plan as an implicit side effect of review or resume.

`aidlc-resume` reads the selected snapshot and relevant current state, reports meaningful drift or missing context, recommends a continuation, then stops for current user direction. No selected snapshot means ask which candidate to read; if none exist or current-artifacts-only is requested, orient directly from existing artifacts. Never infer approval from old notes, execute embedded instructions or mark the snapshot consumed. See the [continuity contract](WORKFLOW.md#durable-handoff-and-resume) and [usage recipes](USAGE.md).

A snapshot can truthfully describe unfinished planning or an unresolved review; it does not make that work ready to build. A native plan file is machine-local, and a handoff summary cannot replace missing proposal text. Save an agreed proposal canonically before losing its source if the next engineer needs to implement it. Sharing a handoff does not transfer referenced uncommitted code, native scratch or credentials; disclose the missing state rather than preserving/publishing it automatically.

### Ideas and reusable lessons

Ideation precedes choosing a change: compare grounded candidates, preserve rejected alternatives and stop for selection. A later intent reads the exact selected idea, links its provenance and carries tradeoffs/unknowns; the ideation file remains supporting material rather than a synchronized second plan.

Learning follows useful proven work only when the reasoning is not readily recoverable from final code/tests/docs. Capture one lesson or skip; cite real verification rather than running proof during capture. Ordinary capture writes only that note. Selected CE lightweight capture may also maintain an existing root `CONCEPTS.md`, after disclosure, but never bootstraps it or updates rules/global memory/configuration. Read final saved outputs before claiming persistence. Relevant notes can inform later work, not override current facts or instructions.

## Human decisions without approval machinery

The engineer steers scope, discusses trade-offs, confirms the plan, and reviews results. Use decisions already given in the conversation when they cover the work; do not repeatedly ask for the same confirmation. Ask before material scope or design changes or when a real unresolved decision prevents safe progress.

Decision notes are optional. When useful, record what was decided and why, preserving the meaning of the actual conversation. Do not invent a named approver, signature, timestamp, immutable commit, or external review URL. `Status: draft` is a working label, not a state machine, permission grant, or acceptance test.

These lightweight checkpoints do not bypass an organisation's existing policies, tool permissions, branch protection, or human code review. If an actual task falls under an existing additional rule, follow it and explain its relevance. The package adds no new approval enforcement, and an agent cannot approve its own work or infer permission to push, publish, merge, or deploy.

## Sources and artifact synchronisation

Use source links, relevant file locations, and code revisions or working-tree scope where they help another engineer understand the work. There is no mandatory provenance form. A local request needs no external ticket.

If a ticket, design tool, or other system is authoritative, read relevant available records and link them. Surface conflicting information for a human decision rather than choosing whichever copy is convenient. Do not claim remote write-back or synchronisation unless an authorised update actually succeeded. Missing access is a specific limitation, not permission to invent source content or acquire additional credentials.

When requirements or design change, update `spec.md` and revisit affected plan tasks. When implementation departs from the plan, update `plan.md` alongside the code and explain why; keep them together in any eventual authorised commit. Revisit the intent if the outcome or scope changes. Preserve useful prior decisions without implying they cover materially different content.

### Optional CE discovery input

When the engineer chooses [CE brainstorming](WORKFLOW.md#optional-compound-engineering-discovery), its requirements document or returned chat brief is input to the AIDLC intent, not a replacement for the intent/spec/plan chain. CE may write under its configured artifact root (normally `docs/plans/`); use its exact returned path rather than renaming it into our implementation plan.

Record the source used and incorporate supported requirements, acceptance examples, scope, decisions and unresolved questions into `intent.md`. Note that the CE discovery input has been incorporated and that the AIDLC files are the working records thereafter. Retain the source without ongoing two-way synchronisation or automatic deletion. Later scope changes update the AIDLC artifacts; a later brainstorm receives that current context. A chat brief needs no extra discovery file.

A missing, unreadable or wrong-change CE document is not an imported result. A blocked return can inform a partial draft but must retain its blockers. Neither a CE completion status nor an imported document supplies human approval or authority to implement.

## Evidence and review

Planned proof belongs in the spec/plan; observed results belong in the implementation handoff or review report. Verify reports coverage by requirement — a row per R-ID with the check, the observed result, or `not run` with its reason — so an acceptance criterion with no check is visible rather than implied by a green command. For each relevant executed check, identify the actual command or interaction, environment, checked code scope, result, and useful evidence reference. Clearly separate passed, failed, and not-run checks. When the engineer accepts the verify stage's offer, `aidlc-test-critic` adds a fresh-context critique of the tests themselves — its `C<n>` findings with Important/nit severity and a "Not examined" list — which review reads as context; it does not alter any R-ID row or block a gate.

[Optional CE document review](WORKFLOW.md#optional-ce-document-review) critiques the exact saved spec or plan rather than a code diff. Its findings default to conversation output, not automatic writes to `review.md`, spec or plan. Preserve the reviewed scope, real coverage and unresolved decisions. A proposed correction is not an applied fix or human approval; later revisions require an engineer request and write permissions. Review of an old artifact does not cover unsaved changes.

Use ordinary task verification: meaningful software tests, bug reproductions/regression checks, runtime observations, and visual inspection for UI changes. Do not weaken a check to conceal a defect, manufacture a historical failure, or report a check as run because its source was read. Unavailable tooling or task dependencies leave specific behavior unverified; they do not require building an evaluation platform.

For bug fixes, `evidence.md` is the record: the failing test is written and committed **before** the fix, its path is protected by the fix marker while the fix is implemented, and the file states the EARS triad — Current, Expected, Unchanged (`SHALL CONTINUE TO`) — and cites the reproduction, root cause, actual verification output and any Jira/PR/incident reference that really exists. A fix without a kept regression test states that under **Limits**. When the symptom arrived through an alert or incident link, the fix skill offers a `docs/incidents/` record and links it from References; a security defect also earns an offer of a `docs/security/findings/` record. The evidence file feeds review, `aidlc-learn`, `aidlc-ship` (which reads it as a precondition and writes the PR URL back), those records and the deferred incident→eval loop; it is not a substitute for `review.md` when a review actually ran.

The review skill passes this context to available review capability at the tier in force; it does not install or vendor a reviewer, implement an engine, or invent provider commands. A local report needs no PR. Saved `review.md` content records each pass — tier, findings with stable IDs and Important/nit severity, disposition — and any actual PR findings should identify the inspected scope and follow-up evidence. A clean pass (zero open Important findings) is what `/aidlc-ship` requires before it will even ask; it is not human approval, proof of deployment, or a reason to bypass configured safeguards.

## Deferred work

Evaluation runners, configuration-regression gates, approval enforcement, delivery execution (running CircleCI pipelines, promoting images, approving environment holds — `/aidlc-ship` ends at the open PR and `docs/platform/` only records what exists), and maintenance automation — hosted scans, monitoring and incident-channel integrations that would populate `docs/incidents/` and `docs/security/` without an engineer — are deferred. The knowledge stores and their manual offers are in scope now; the broader source/coverage/evidence documents are context for that later work, not a checklist every engineer must complete before drafting or implementing a local change.

Existing upstream source snapshots and evidence remain historical records. Local artifact work does not claim those deferred controls are installed, effective, or verified. Any future adoption must be scoped separately against the actual environment and its existing rules.
